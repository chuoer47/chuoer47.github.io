# 07 · 成员变量与缓冲生命周期总表

本篇覆盖 `src/00e39ab5/op_kernel/chunk_gated_delta_rule.h` 第 **917-966** 行（50 行的 `private:` 声明区 + 文件尾）。这段代码本身不含任何逻辑，但它是前三篇所有推断的落点：**报告 2/3 里凡是要问"这块 UB 此刻装着什么、还能不能安全覆写""这个标量在设备侧到底有没有被读过"，都以本篇两张表为准**。结论先行：

1. 50 行声明里住着 **44 个成员**：10 个 `GlobalTensor`（GM 句柄）、1 个 `TPipe*`、1 个 `TQue`、1 个 `TBuf`、11 个 `LocalTensor`（全部是 `tmpBuff` 的切片）、20 个标量成员。**任务书里说的"18 个标量成员"只数了 `uint32_t`（:944-961 共 18 行）**，另有 `float scale_`（:962）与 `uint64_t blockIdx_`（:963），合计 20。
2. 11 个 `LocalTensor` 的**声明注释就是权威尺寸公式**，与 :156-194 的实际分配量逐条对得上（§3 表的最后一列给出核对结果）；只有 `dotProductFp32`（:941）的注释是描述性的、没给公式，真实尺寸是 `max(stateStrideK_, chunkSize_)`（:186/:191）。
3. 缓冲的生命周期只有三种形态：**常驻整 kernel**（11 块 UB 切片 + 队列 + GM 句柄）、**每 chunk 重生**（K 侧 5 块）、**每 V-tile 重生**（V 侧 4 块）。没有任何一块是"每 token"或"每 head"重生的。
4. 21 个"值语义"成员（20 个标量 + `pipe_`）**全部在构造函数里被赋确定值**（:76-:98），其中 `pipe_`/`vStepAligned_`/`blockIdx_`/`load_`/`usedblk_`/`avgload_` 六个是"先占位、后真赋值"；另外 23 个（10 个 `GlobalTensor` + 11 个 `LocalTensor` + `tmpBuff` + `stateOutQueue_`）分别由 `SetGlobalTensors` :113-:124 与 `InitLocalBuffers` :138/:153/:156-:194 生效。真正的**死成员只有 2 个**：`T_`（:945）与 `numChunks_`（:953）。
5. UB 尺寸公式在 host（`ComputeTmpBuffBytes`）与 device（`InitLocalBuffers` 的 `off` 累加）里**各写了一遍**，两者必须一致；本篇 §10 给出等价的三条不变式并逐情形证明，这是后续 PR 改动时最容易踩的雷。

- :917 的 `private:` 是**冗余重申**：类体从 :74 起为 `public:`，第一个 `private:` 在 :238，其后直到 :964 再没有 `public:`，所以 :239-:916 的 29 个 helper 早就私有化了。`public:` 区（:74-:237）共 6 个函数：构造 :75、`Init` :101、`SetGlobalTensors` :112、`InitLocalBuffers` :127、`ComputeAvgload` :197、`Process` :209；入口 cpp 只调后二者的 `Init`/`Process`（cpp:34、cpp:35），另 4 个属"公开但仅供自身调用"。全类 35 个成员函数，另有 1 个文件级模板函数 `CopyToGm`（:41-:57）。这个划分说明作者刻意把 kernel 当成一个只有两个动作的对象，而不是一组可复用的算子库。
- 模板参数 `inType`/`outType`（:72）在入口被实例化为 `<half, half>`（cpp:33）。所以本篇里 `sizeof(inType) == 2`、`sizeof(outType) == 2`、`float == 4` 是**实例化事实**而非假设；`gGm_` 是唯一的 `float` 输入、`stateWorkspaceGm_` 是唯一的 `float` workspace，其余 GM 都是 FP16。
- `GlobalTensor<T>` 机器语义：只存一个 `__gm__ T*` 的**薄句柄**（无长度、无所有权），`SetGlobalBuffer` 装地址、`GetValue/SetValue` 走标量访存、`DataCopy(dst[offset], ...)` 里的下标只是元素偏移量。**它不做边界检查**，所以 §2 的"未 Set 即未定义"是真实风险而不是教条。
- `TPipe *pipe_` 是裸指针，指向 cpp:32 栈上的 `TPipe pipe`。生命周期由入口函数保证（对象 `op` 与 `pipe` 同作用域）；这也是为什么 `pipe_` 必须在 `Init` 里赋值而不能在构造里拿到。

三条要点：

- **同一份数据两种访问路径**是"快/慢双路"的代价：K 在 Phase 1 用 DMA 进 UB（:467），Step 7 又从 GM 逐标量重读（:867）；Q 在 Phase 3.5 用 DMA 进 UB（:564），Step 5 又从 GM 逐标量重读（:821）。原因不是"忘了缓存"，而是**缓存它们的 UB 被别人占了**（§7 的借尸清单）。
- 装填顺序无隐含依赖，但 :119 的**条件装填**使 `hasGamma_` 成为唯一一个能改变"句柄是否有效"的标量成员。任何新增的 `gGm_` 读取都必须先看 `hasGamma_`，否则读到未定义基址；目前只有 :255 一处读，且被 :252 挡住 ✓。注意 `CGDRInitParams`（:59-:70）里 `gOptional` 排在第 7 个、`attnOut`/`finalState`/`workspace` 在后，而 :122/:123 的赋值顺序是 finalState 再 attnOut —— **结构体字段顺序与成员顺序不一致，靠名字取字段所以无害**，但逐字段对照时容易看错。
- `stateWorkspaceGm_` 是唯一"既读又写"的 GM，也是唯一由 `GetUserWorkspace` 提供的缓冲（:124 装的是 `initParams.workspace`，而该字段由 cpp:29-:31 填成 `GetUserWorkspace(workspaceGM)`）。host 申请的字节数是 `max(B·Nv·dk·ceil8(dv)·4, 32 MiB)`（tiling.cpp :286-:289 + `kWorkspaceBytes` :39），与 kernel 的**实际用量** `B·Nv·dk·stateWorkspaceStrideV_·4` 之间只有单向包含关系（32 MiB 下限是白给的，02 篇）。

求和（示例配置）：

- 重叠分支（:168-172）：`32+32+16+4+16(共享)+4+0.25+0.5+0.5+0.25 = 105.5 KiB`
- 非重叠分支（:173-177）：`stateInFp32` 另占 8 KiB ⇒ `113.5 KiB`
- 外加 `stateOutQueue_` 的 `max(sk·av·2, cs·av·2) = max(4096, 2048) = 4 KiB`（:134-138）
- `tmpBuff` 的申请量 `restUbSize_` 恒为 `ubSize - outQueueMax`（host :187），即**除队列外全部 UB 交给切片**；因此"切片之和 ≤ restUbSize_" 由 host 的 `SolveVStep` 反向挑选 vStep 来保证（§10）。

`dotProductFp32` 那行的真实约束值得单列，因为它是**注释里唯一没有公式、却决定安全性**的一条：`DotFp32` 的 `count` 全部是 `realK_`（:580/:592/:608），而 `Mul`（:290）按 `count` 写满、`WholeReduceSum`（:297）就地回写 partials。分配量 `max(sk, cs) ≥ sk ≥ dk = realK_` ⇒ **写入永不越界**；partials 只落在 `[0, 8·fullRepeats)`、尾部乘积只落在 `[64·fullRepeats, count)`，两段不相交（`8·fullRepeats ≤ count/8 < 64·fullRepeats`）⇒ :305 与 :309 的读区互不覆盖；04 篇 §6 另外给了就地归约不越界所需的上界 `count ≤ 512`，它由 `realK_ ≤ sk` 与 host 对 dk 的合法域（本篇 §10 不变式③）共同满足。

四条观察：

- **"先占位后真赋值"共 6 个成员**（:91-:93/:96-:98），这不是风格洁癖：`ShouldSplitVTiles()`（:239）被 `InitLocalBuffers`（:168）和 `ComputeAvgload`（:205）调用，而 `IsCurrentBlock` 读 `blockIdx_/load_/avgload_`；一旦哪天有人把 `ComputeAvgload` 提到 `Init` 之前，占位值会让它退化而不是读到垃圾。
- `restUbSize_` 只被 :153 读一次，**且读之前不做任何校验**：`InitBuffer(tmpBuff, restUbSize_)` 直接吃 tiling 里的数。若 host/device 的 vStep 或重叠判定不一致（§10），后果是切片之和超出 `tmpBuff` 而**没有任何断言会响**。:194 之后连 `off` 的终值都没人和 `restUbSize_` 比对——这是本 kernel 最实的一处结构性缺口。
- `Init` 的 :104-106 `blockIdx_ >= blockDim` 早退在当前配置下**永不触发**（host `SetBlockDim(blockDim)`，:275-279 ⇒ `GetBlockNum() == blockDim`），但入口 cpp:35 **无条件调用 `op.Process()`**：真触发的话 `Process` 会带着 `pipe_ == nullptr` 与未装填的 GM 句柄跑下去，`ComputeAvgload` 的第一次 `GetValue` 即崩。安全来自"launch 维 == blockDim"这条隐式约定，不是来自这个 guard。
- `T_`/`numChunks_` 两个死成员（:945/:953）只赋值不读取。它们的价值是**与 host tiling 结构体逐字段镜像**，方便 `CGDR_DEBUG_LOG` 对账；代价是读者会误以为 kernel 按 `T_` 算长度。真实语义是：序列长度取自 `actualSeqLengthsGm_`（变长、逐 batch），块数在 :382/:396 现算。

- `stateStrideK_` 用 `FP32_NUM_PER_BLOCK`（8）而 `alignK_` 用 `FP16_NUM_PER_BLOCK`（16）：**因为前者索引 FP32 行（32B = 8 个 float）、后者索引 FP16 行（32B = 16 个 half）**。`vStepAligned_`/`stateWorkspaceStrideV_` 都按 8（服务 FP32 tile）。这一处不对称是全文件最容易看错的一行（:88 vs :89-:90）。

## 10. 与 host 的对账：两套尺寸公式、三条不变式

同一个 tmpBuff 用量被写了两遍：host 的 `ComputeTmpBuffBytes`（tiling.cpp :128-:148）与 device 的 `off` 累加（:156-194）。要让 `restUbSize_` 永远够用，需要下面三条同时成立，本篇逐条核过：

- **不变式①（切片集合相同）**：host 逐项列出 `2×cs×alignK + cs² + cs×av + (scores/state) + cs×av + cs + delta + dot + cs`，与 :156-194 的 11 项一一对应，顺序相同 ⇒ 字节数逐位相等。✓
- **不变式②（重叠判定相同）**：host 用 `overlapScoresState = (vs >= dv) || allowScoresStateOverlap`，其中 `allowScoresStateOverlap = (dims.hv < aivNum)`（:254）；device 用 `vStep_ >= realV_ || ShouldSplitVTiles()`（:168），后者 = `dv > vStep && GetBlockNum() > hv`。四情形枚举：
  - `vStep ≥ dv`：两侧都重叠 ✓
  - `vStep < dv ∧ hv < aivNum`：`blockDim = min(hv·vTileCount, aivNum) > hv`（因 `vTileCount > 1` 且 `aivNum > hv`）⇒ device 也重叠 ✓
  - `vStep < dv ∧ hv ≥ aivNum`：`blockDim = min(hv, aivNum) = aivNum ≤ hv` ⇒ device 不重叠，host 也不重叠 ✓
  - `vTileCount == 1` 归入第一条 ✓
  **⇒ 恒一致**，但一致性依赖 `SetBlockDim` 的 `blockDim = min(workItems, aivNum)` 规则（:275）。改动 blockDim 计算方式（例如恒用 aivNum）会直接造成 device 比 host 多要 8 KiB ⇒ UB 静默越界。
- **不变式③（vStep 选得下）**：`SolveVStep` 从 `maxVStep = CeilAlign(dv, 16)` 起、按 16 递减枚举到 16（tiling.cpp :167-:178），取第一个满足 `tmpBuff + outQueue ≤ ubSize` 的值 ⇒ 两个含义：① `vStep_` 恒为 16 的倍数 ⇒ `vStepAligned_ == vStep_`（声明注释里两个名字是同一个数）；② `vStep_` **可以大于 `dv`**（当 dv 不是 16 倍数时 `CeilAlign(dv,16) > dv`），这正是 :168 要写 `vStep_ >= realV_` 而不是 `==` 的原因。顺带一条：host :182-:184 的 `if (vStepVal > dv) vStepVal = CeilAlign(dv, 16);` 在数学上是**恒等赋值**（枚举起点就是 `CeilAlign(dv,16)`，比它大的候选不存在），所以这段代码只是把 :159 注释里 "<= dv" 的说法圆回来，没有实际效果。
- 附带一条 host 侧事实：`kExpTaylorTerms`、`alignK_` 等派生量**不进 tiling**，device 自己从 `dk/dv` 重算（:88-90），host 也算一遍（tiling.cpp 里 `alignK`）⇒ 派生公式也是"两份实现"，改 `Ceil` 的基数（8/16）必须同时改两处，否则 §3 表的"示例字节"就会与 host 的预算脱钩。

## 11. 交给后续报告的五条硬结论

1. **UB 是唯一稀缺资源**：`restUbSize_`（:955）被 :153 一次性用光，11 块切片无余量校验；因此"要不要缓存 Q/K"不是设计偏好，而是 `max(cs², sk·av)` 与 `cs·vStepAligned_` 之间的算术（§3 求和）。
2. **性能与 UB 的直接因果**：Q/K 二次回 GM 标量读（:821/:867）造成的 1.65 万次/`(chunk,tile)` 标量访存，其根源就是 §3 表里那 16 KiB 的 scores 与 8 KiB 的 state 抢走了位置。任何"加大 vStep""合并 scores/state"的改动都必须同时报 host `ComputeTmpBuffBytes` 的新值。
3. **`vStepAligned_` 与 `stateWorkspaceStrideV_` 不可混用**（:956-958），它们分别管 tile 行 stride 与 workspace 行 stride；06 篇 §14 的 stride 总表是它们的全部用场。
4. **删同步的安全边界**：读列里出现"标量读 UB"（`GetValue`）的位置就是必需的 V→S 同步的位置——实测清单是 **17 处标量读 UB**（:305/:309、:320、:331、:524、:581、:593、:609、:621、:635、:740、:796、:819、:838、:853、:864、:911）+ **10 处标量写 UB**（:320、:480、:490、:581、:586、:594、:602、:610、:726、:778），去重后 25 行（:320/:581 同行读写）。这些行是不可删的 S↔V 同步点；不落在清单里的 `TQueSync`/`PipeBarrier` 都是保守写法，可批量删（05 篇 §13、06 篇 §16 的"保守"标签由此而来）。另有 10 行标量读 GM（:200/:213/:255/:259/:480/:602/:725/:778/:821/:867），它们只要求 S 管道自身的顺序性，不需要与 V 同步。
5. **两个死成员、一个永不触发的 guard、一处无校验的 `InitBuffer`**：`T_`（:945）、`numChunks_`（:953）、`Init`:104-106、`restUbSize_`:153。它们是后续 review 的第一个检查清单。
