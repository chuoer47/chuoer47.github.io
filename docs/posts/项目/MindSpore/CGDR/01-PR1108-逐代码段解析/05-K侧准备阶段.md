# 05 · K 侧准备阶段：Phase 1~5 与四层编排

本篇覆盖 `src/00e39ab5/op_kernel/chunk_gated_delta_rule.h` 第 **374-648** 行。结论先行：

1. 这 275 行是**编排层（4 个 `Process*`）+ 准备层（7 个 Phase 函数）**。编排层没有任何向量指令，准备层才是全部 K 侧算法。
2. Phase 1~5 与 V 维无关，产出三样跨 V-tile 复用的东西：`chunkScoresFp32`（逆矩阵 A）、`chunkKFp32`（被覆盖成 K_cd）、`decayMaskFp32`（被覆盖成 QK 注意力矩阵）。**"每 chunk 一次"与"每 tile 一次"的分界就在 `ProcessChunk` 的最后一行（:420）**。
3. 本区间共有 **9 处 `TQueSync` 对象 + 3 组事件三段式**。它们不是同一种东西：有 3 处是真正必需的"标量写 UB → 向量读 UB"，有 3 处是块级保守收口，有 3 处只是给标量侧的行系数"发指令前打点"。逐处给理由见 §13 的总表。

## 1. ProcessHead：一个 value-head 的全部 chunk

锚点：chunk_gated_delta_rule.h:374-386

```cpp
  __aicore__ inline void ProcessHead(int32_t seq0, int32_t seq1, uint64_t head_i, uint64_t batch_i) {
    uint64_t nvPerNk = (NV_ >= NK_) ? (NV_ / NK_) : 1;
    uint64_t qkHead = head_i / nvPerNk;
    uint64_t stateBaseOffset = (batch_i * NV_ + head_i) * realK_ * realV_;
    uint64_t workspaceStateBaseOffset = (batch_i * NV_ + head_i) * realK_ * stateWorkspaceStrideV_;
    uint32_t cs = chunkSize_;
    int32_t totalLen = seq1 - seq0;
    uint32_t numC = Ceil(static_cast<uint32_t>(totalLen), cs);
    for (uint32_t c = 0; c < numC; c++) {
      ProcessChunk(seq0, seq1, head_i, c, qkHead, stateBaseOffset, workspaceStateBaseOffset, c + 1 == numC);
    }
  }

```

逐行：

- :375 `nvPerNk`：GQA 式分组。`NV_ < NK_` 时取 1（不做除法，避免 `head_i/0` 之外的整数截断意外，且此时语义是"每个 V-head 用自己的 QK-head"）。约定 `NK_` 整除 `NV_`，否则该映射会退化，kernel 不校验（tiling 侧也不校验，属隐式前置条件）。
- :376 `qkHead`：**Q/K 的一切 GM 偏移只用 qkHead；beta/g/state 的偏移只用 head_i**。这个二分贯穿全 kernel（:457/:478/:553/:600/:818/:863 用 qkHead，:255/:259/:503/:706 用 head_i），混用会造成静默的跨 head 数据污染。
- :377/:378 两个 state 基址：前者是公共接口 `[B, Nv, dv, dk]`（元素数 `dk*dv`，乘积顺序不影响基址但影响行内寻址，见 06 篇 §3），后者是 kernel 自定义 workspace `[B, Nv, dk, align32(dv)]`。同一 head 的起始元素偏移都是 `(b·NV_+h)·dk·宽度`，差别只在宽度取 `realV_` 还是 `stateWorkspaceStrideV_`。
- :381 `numC = Ceil(totalLen, cs)`：**按本 batch 真实长度算块数**，不读 tiling 的 `numChunks_`。所以 `numChunks_`（:953）与 `T_`（:945）在本 commit 里是**只赋值不读取的死成员**（实测：`T_` 只出现在 :77/:945，`numChunks_` 只出现在 :84/:953）。它们的存在是为了与 host tiling 结构体字段一一镜像，便于 `CGDR_DEBUG_LOG` 对账。
- :383 `c + 1 == numC` 就是 `isLastChunk`，决定 state 写 FP32 workspace 还是 cast 成 FP16 写 `finalState`（06 篇 §9）。

chunk 之间**严格串行**（$S_c$ 依赖 $S_{c-1}$），这是本 kernel 唯一的真依赖链，也是"按 head/tile 分核、不按 chunk 分核"的根本原因：chunk 维不可并行，只能整条分给一个核。

## 3. ProcessChunk：八段 phase 的唯一编排点

锚点：chunk_gated_delta_rule.h:404-422

```cpp
  __aicore__ inline void ProcessChunk(int32_t seq0, int32_t seq1, uint64_t head_i, uint32_t c, uint64_t qkHead,
                                      uint64_t stateBaseOffset, uint64_t workspaceStateBaseOffset, bool isLastChunk) {
    uint32_t cs = chunkSize_;
    uint32_t avFp32 = vStepAligned_;
    int32_t totalLen = seq1 - seq0;
    int32_t t_start = seq0 + c * cs;
    uint32_t chunkLen =
      (static_cast<uint32_t>(totalLen) - c * cs >= cs) ? cs : static_cast<uint32_t>(totalLen) - c * cs;

    LoadChunkKey(qkHead, t_start, chunkLen);
    ComputeGCumsum(t_start, head_i, chunkLen);
    ComputeKBeta(t_start, head_i, chunkLen);
    PrepareDecayAndExp(chunkLen);
    PrepareAttnQueryCache(qkHead, t_start, chunkLen);
    ComputeAttnMatrix(qkHead, t_start, chunkLen);
    ComputeKCumdecay(chunkLen);
    ProcessVTiles(t_start, chunkLen, head_i, qkHead, avFp32, stateBaseOffset, workspaceStateBaseOffset, c, isLastChunk);
  }

```

- :410-411 `chunkLen`：在 uint32 域里比较 `totalLen - c*cs >= cs`，尾块取余数。这个式子保证 `1 ≤ chunkLen ≤ cs`（因为 `c < numC` ⇒ `c*cs < totalLen`）。**所有三角循环的上界都是 `chunkLen`，所有行跨距/缓冲宽度都是 `chunkSize_`（`ld`）**——这一对区分是本 kernel 处理变长尾块不越界的全部依据（尾块之后未写到的矩阵元素保持上一 chunk 的残留，但因为读的时候同样只用 `< chunkLen`，永远读不到）。
- :407 `avFp32 = vStepAligned_`：V 侧所有行宽都用它。
- :413-419 的顺序是**硬约束**，逐条给出理由：
  1. `LoadChunkKey` → `ComputeKBeta`：后者 :506 读 `chunkKFp32`。
  2. `ComputeGCumsum` → `PrepareDecayAndExp`：后者 :516-527 读 `gCumsumFp32`。
  3. `PrepareDecayAndExp` → `ComputeAttnMatrix`：:581/:593 读 `decayMaskFp32`、:621（Phase 5）读 `expGCumFp32`。
  4. `PrepareAttnQueryCache` → `ComputeAttnMatrix`：后者 :590 读缓存。**且它必须排在 Phase 1/Phase 3 之后**——它借 `chunkVFp32` 当 FP16 暂存（:552），而 Phase 1 也借同一块（:456）：两次借用之间必须有一次把前一次的数据用完（Phase 1 的 `Cast` 在 :471 完成消费）。所以 Phase 3.5 不能提前到 Phase 1 之前。
  5. `ComputeAttnMatrix` → `ComputeKCumdecay`：后者 :635 读 A。
  6. `ComputeKCumdecay` → `ProcessVTiles`：Step 4 用 K_cd，且 K_cd 覆盖在 `chunkKFp32` 上——覆盖之后原始 K 在 UB 里就没了，所以任何还需要 UB 里原始 K 的阶段都必须排在前面（Phase 4 正是最后一个使用者）。
  7. `PrepareAttnQueryCache` 还必须排在 `ProcessVTiles` 之前：它把 Q 缓存放进 `chunkAttnOutFp32`，而 Step 1（:687）会把同一块借去当 V 的 FP16 暂存。**Q 缓存在 Phase 4 之后立刻变成死数据**，这正是 Step 5 只能从 GM 现读 Q（:821）的原因——一条完整的因果链（06 篇 §6）。


:433-439 与 :413-419 完全相同 ⇒ **tile 模式下 K 侧准备被执行 `vTileCount` 次**（每个负责一个 V-tile 的核各做一遍）。这不是疏漏而是设计：Phase 1~5 的产出是每核私有 UB 里的数据，跨核无法共享（本 commit 没有任何跨核通信原语）；而该模式的启用条件（`ShouldSplitVTiles`）恰好是"核有空闲"，此时冗余计算的时间是**白送的**（并行度收益 > 冗余成本）。当 `vTileCount` 大到核不再空闲时，host 侧就不给这么大的 blockDim 了（`blockDim = min(hv·vTileCount, aivNum)`）。

:440-441 的 `v_i`/`curV` 与 `ProcessVTiles`（:652-653）里的循环体是同一对公式的两种写法。二者必须永远等价，否则 tile 模式下最后一个 tile 会少算/多算 `dv % vStep` 列。

## 5. LoadChunkKey：2D strided DMA 快路径与非对齐回退

锚点：chunk_gated_delta_rule.h:447-485

```cpp
  __aicore__ inline void LoadChunkKey(uint64_t qkHead, int32_t t_start, uint32_t chunkLen) {
    uint64_t stagingCapacity = static_cast<uint64_t>(2) * chunkSize_ * vStepAligned_;
    uint64_t keyElements = static_cast<uint64_t>(chunkLen) * realK_;
    uint64_t gmRowStride = static_cast<uint64_t>(NK_) * realK_;
    uint64_t srcGapBytes = (gmRowStride - realK_) * sizeof(inType);
    bool canUseDma = chunkLen <= UINT16_MAX && keyElements <= stagingCapacity && alignK_ == realK_ &&
                     (realK_ * sizeof(inType)) % BLOCK_BYTES == 0 && srcGapBytes % BLOCK_BYTES == 0 &&
                     srcGapBytes / BLOCK_BYTES <= UINT16_MAX;
    if (likely(canUseDma)) {
      LocalTensor<inType> keyLocal = chunkVFp32.template ReinterpretCast<inType>();
      uint64_t qkOff = (static_cast<uint64_t>(t_start) * NK_ + qkHead) * realK_;
      DataCopyParams keyParams{static_cast<uint16_t>(chunkLen),
                               static_cast<uint16_t>(realK_ * sizeof(inType) / BLOCK_BYTES),
                               static_cast<uint16_t>(srcGapBytes / BLOCK_BYTES), 0};
      event_t scalarToMte2 = static_cast<event_t>(pipe_->FetchEventID(HardEvent::S_MTE2));
      SetFlag<HardEvent::S_MTE2>(scalarToMte2);
      WaitFlag<HardEvent::S_MTE2>(scalarToMte2);
      event_t vectorToMte2 = static_cast<event_t>(pipe_->FetchEventID(HardEvent::V_MTE2));
      SetFlag<HardEvent::V_MTE2>(vectorToMte2);
      WaitFlag<HardEvent::V_MTE2>(vectorToMte2);
      DataCopy(keyLocal, keyGm_[qkOff], keyParams);
      event_t mte2ToVector = static_cast<event_t>(pipe_->FetchEventID(HardEvent::MTE2_V));
      SetFlag<HardEvent::MTE2_V>(mte2ToVector);
      WaitFlag<HardEvent::MTE2_V>(mte2ToVector);
      Cast(chunkKFp32, keyLocal, RoundMode::CAST_NONE, chunkLen * realK_);
      PipeBarrier<PIPE_V>();
      return;
    }

    for (uint32_t i = 0; i < chunkLen; i++) {
      int32_t t = t_start + i;
      uint64_t qkOff = (static_cast<uint64_t>(t) * NK_ + qkHead) * realK_;
      for (uint32_t j = 0; j < realK_; j++) {
        chunkKFp32.SetValue(i * alignK_ + j, static_cast<float>(keyGm_.GetValue(qkOff + j)));
      }
    }
  }

  // Phase 1b: cumulative sum of g into gCumsumFp32.
```

**为什么需要暂存 + Cast 两步而不是 DMA 直接进 FP32**：GM 里 K 是 FP16，UB 目标 `chunkKFp32` 是 FP32，`DataCopy` 不做类型转换，所以必须先按 FP16 搬进一块 FP32 空间（省不到第二块缓冲），再用向量 `Cast` 无损扩展。

- :448 `stagingCapacity = 2·cs·vStepAligned_`：借的是 `chunkVFp32`，容量 `cs·vStepA` 个 FP32 = `cs·vStepA·4` 字节；按 FP16 元素数就是 `2·cs·vStepA`。**因子 2 正是 FP32→FP16 的元素数翻倍**，不是保守估计。
- :449 `keyElements = chunkLen·realK_`：待搬的 FP16 元素数（K 无 padding，紧凑）。
- :450-451 `gmRowStride = NK_·realK_` 是 GM 的行跨距（一次 `t+1` 要跳过的元素数），`srcGapBytes = (NK_-1)·realK_·2` 即"跳过同一 token 其余 K-head"。
- :452-454 六个条件逐个：`chunkLen ≤ UINT16_MAX`（blockCount 是 u16，cs=64 恒成立，防御）、`keyElements ≤ stagingCapacity`（借的暂存装得下）、`alignK_ == realK_`（**关键**：见下）、`realK_·2 % 32 == 0`（FP16 行宽整块）、`srcGapBytes % 32 == 0`（gap 整块）、`srcGapBytes/32 ≤ 65535`（gap 塞得进 u16）。

**`alignK_ == realK_` 为什么同时挡住两件事**：:471 的 `Cast(chunkKFp32, keyLocal, ..., chunkLen*realK_)` 是**扁平一次转**，源和目标都按连续元素排。目标 `chunkKFp32` 的行宽是 `alignK_`（:156 用 `cs*ak` 分配），只有 `alignK_ == realK_` 时"连续第 m 个元素"才恰好等于"第 m/realK_ 行第 m%realK_ 列"。否则需要逐行 `Cast` 并在目标侧留 gap——`Cast` 这类逐元素向量指令没有 dstGap 参数，只能写成 64 次调用。所以这一个条件同时保证了"FP16 暂存紧凑"和"FP32 目标无 padding"，快路径才有可能只用一条 DMA + 一条 Cast。

- :456 `chunkVFp32.template ReinterpretCast<inType>()`：只改类型视图不改地址，此刻 `chunkVFp32` 的原主人（V 数据）还没被加载（Phase 6 Step 1），借用合法。
- :458-460 `DataCopyParams{blockCount, blockLen, srcGap, dstGap}` = `{chunkLen 行, 每行 realK_·2/32 块, 行末跳 (NK_-1)·realK_·2/32 块, UB 侧不跳}`。`DataCopyParams` 的四字段**单位都是 32B block**（blockCount 除外，它是行数），这正是三个 `% BLOCK_BYTES` 判定的由来。
- :461-466 事件三段式的前两段：MTE2 即将**覆写** UB 暂存区，所以必须先确认（a）标量管道此前对该区间的写已结束（`S_MTE2`）、（b）向量管道此前对该区间的读已结束（`V_MTE2`）。`SetFlag` 与 `WaitFlag` 成对：前者由"源侧"打点，后者由"目的侧"等待；中间没有别的指令，所以它实际是"就地阻塞直到上一批动作完成"。
  为什么用 `pipe_->FetchEventID(HardEvent::X_Y)` 而不是 `TQueSync<X,Y>`：`TQueSync` 是队列级的方向性同步（S/V 之间用它最顺手），而 MTE 与 S/V 的配对在 API 上暴露为硬件事件 ID，需要先从 `TPipe` 要一个空闲 ID（`FetchEventID`），再 `SetFlag/WaitFlag<HardEvent::X_Y>`。事件 ID 是**每核有限的资源**，所以要 `FetchEventID` 而不是写死数字。
- :471 `chunkLen * realK_` 用真实元素数（不含 tail padding）：暂存区可能有剩余空间是脏的，但只转 chunkLen 行 × realK_ 列 ⇒ `chunkKFp32` 的行 padding 不被本路径写（后续所有读取都用 `realK_` 为长度，不触及 padding，见 §7 末尾）。
- :472 `PipeBarrier<PIPE_V>`：`Cast` 之后立刻返回，函数出口处必须保证向量写完成——因为 `ComputeKBeta` 的第一个动作是 `TQueSync<PIPE_S,PIPE_V>`（:498），那是 S→V 方向，**挡不住向量写对向量读的可见性**。
- :473 `return`：快路径结束，绝不落入慢路径。
- :474 之后的 `for`（:476-482）是慢路径：`chunkLen × realK_` 次标量 GM 读 + 标量 UB 写（最坏 8192 次访存/块，比快路径慢一到两个量级）。它直接写 FP32 目标且**用 `alignK_` 作行宽**（:480），所以 `alignK_ ≠ realK_` 时行 padding 仍然存在（但不被读）。`static_cast<float>(keyGm_.GetValue(...))` 把类型转换搬到标量侧，省掉 `Cast` 与暂存区——这就是慢路径不需要 `chunkVFp32` 也能工作的原因。

**`DataCopyParams` 与 `DataCopyExtParams` 的分工**（本区间只用前者，后者见 04 篇 :366）：

| 结构 | 字段 | 单位 | 能力 |
|---|---|---|---|
| `DataCopyParams` | `{blockCount, blockLen, srcGap, dstGap}` | 块数（32B） | 快，但行宽与两侧 gap 必须 32B 整除 |
| `DataCopyExtParams` | `{blockCount, blockLen, dstStride, srcStride, srcL1Size}` | blockLen 是**字节**，stride 是字节 | 允许非整块搬运；`blockCount` 可为 1，配 `CopyToGm`(:41-57) 做"整块直搬 / 非整块逐块 + `PipeBarrier<PIPE_MTE3>`"回退 |

`CopyToGm` 的回退逻辑就是"非对齐回退"的正例：`alignElem == elem` 时转成 `DataCopyParams`；否则 `blockCount=1` 逐行搬、每行一次 MTE3 栅栏。`test_non_multiple_reduce_width`（docs/PR-406 §4.4）覆盖的正是 `dk/dv` 非 32B 倍数时 `canUseDma=false` 的整条慢路径。

## 6. ComputeGCumsum：块内前缀和（不是全局前缀和）

锚点：chunk_gated_delta_rule.h:486-494

```cpp
  __aicore__ inline void ComputeGCumsum(int32_t t_start, uint64_t head_i, uint32_t chunkLen) {
    float gSum = 0.0f;
    for (uint32_t i = 0; i < chunkLen; i++) {
      gSum += LoadG(t_start + i, head_i);
      gCumsumFp32.SetValue(i, gSum);
    }
  }

  // Phase 2: k_beta = K * beta -> kCumdecayFp32.
```

- `gSum` 每 chunk 从 0 起 ⇒ `G_i` 是**块内**前缀和。这是 chunkwise 算法的数学要求：所有用到 G 的地方（`e^{G_i}`、`e^{G_i-G_j}`、`e^{G_{L-1}}`）都是块内相对量，块间耦合全部由 state 矩阵承担。**后果是结果对 chunkSize 不敏感的前提**（配合 FP32 workspace 传 state，见 01 篇 §6）；若这里是全局前缀和，换 chunkSize 就会改变衰减因子的数值组合顺序。
- 纯标量 64 次：加法链不可向量化（真依赖），且长度远小于一条向量指令的 64 元素宽度。`SetValue` 走标量管道写 UB ⇒ 下游 Phase 2/3 的 S→V 同步与 `Muls(×1.0)` 刷新（:516）都是为它服务。
- `LoadG` 返回 0 时本函数变成"写 64 个 0"，`hasGamma_ == 0` 的整个成本就是 64 次标量写。

## 8. PrepareDecayAndExp：exp 预计算与 decay 行的构造

锚点：chunk_gated_delta_rule.h:514-533

```cpp
  __aicore__ inline void PrepareDecayAndExp(uint32_t chunkLen) {
    uint32_t cs = chunkSize_;
    Muls(gCumsumFp32, gCumsumFp32, 1.0f, cs);
    PipeBarrier<PIPE_V>();
    Exp(expGCumFp32, gCumsumFp32, cs);

      PipeBarrier<PIPE_V>();
      Sub(deltaFp32, deltaFp32, gCumsumFp32, cs);
      PipeBarrier<PIPE_V>();
      Exp(decayMaskFp32[i * cs], deltaFp32, cs);
      PipeBarrier<PIPE_V>();

```

- :516 `Muls(×1.0f, cs)`：`gCumsumFp32` 由标量管道写（:490），紧接着 :518 的 `Exp` 由向量管道读 ⇒ 需要"向量管道整体过一遍 + `PipeBarrier`"。这与 04 篇 :345、06 篇 :898 是同一惯用法。**注意长度是 `cs`（64）不是 `chunkLen`**：尾块时 `[chunkLen, 64)` 区间是**上一 chunk 的残留**，这里把它们一并过一遍向量管道，保证 `Exp` 读的 64 个 lane 都是"向量管道写过的 UB"，不残留标量管道未落地状态。
- :518 `Exp(expGCumFp32, gCumsumFp32, cs)`：一条指令算 64 个 $e^{G_i}$（硬件 exp 查表 + 插值）。写入 `expGCumFp32`，长度 `cs` ⇒ 同样覆盖到残留区（见下"溢出隐患"）。
- :520-522 `expSync`（V→S）：这是**全 kernel 关键的一条**。此后所有标量侧读 `gCumsumFp32`（:524、:864）、`expGCumFp32`（:621、:819、:853）、`decayMaskFp32`（:581 起）之前，都会先越过这一个 V→S 点（或被 :300-302 `DotFp32` 内部的同类点覆盖）。删掉它，Phase 5 的 `gExp` 与 Step 7 的 `gLastExp` 都可能读到旧值。
- :523-531 每行四步：标量取 $G_i$ → `Duplicate` 广播成 `[G_i]×64` → `Sub` 得 `deltaFp32[j] = G_i - G_j` → `Exp` 写 `decayMaskFp32` 第 i 行 64 列。三条 `PipeBarrier<PIPE_V>` 是**同一条管道上的 WAR/WAW 保序**：`deltaFp32` 被连续读写三次（写、读改写、读），下一行的 `Duplicate` 也不能早于上一行的 `Exp` 读它。
- 每行 `Exp` 的宽度是整 `cs=64`，包括 $j \ge i$（上三角）。$g \le 0$ 时 $G$ 单调不增 ⇒ 上三角的 $G_i - G_j > 0$ ⇒ **$e^{(\cdot)} > 1$**，即 decay 缓冲里"合法但有害"的值真实存在。
- **lower-triangular 到底在哪里构造**：`decayMaskFp32` 本身是**完整 64×64 的 $e^{G_i-G_j}$，并不是下三角**；因果性（三角性）完全由**四个消费点的循环上界**保证：:578-579 `jj < i`（A 的严格下三角）、:591/:607 `jj <= i`（QK 覆盖只写下三角+对角）、:837 `jj <= i`（`AccumOutput` 只累加历史）。所以下三角是"读出来的"，不是"造出来的"。这个分工换来一次 `Duplicate+Sub+Exp` 覆盖整行（向量效率最高），代价是必须靠纪律（三处上界一致）而非数据布局来守因果性——若上界写错，$j>i$ 的未来信息会以 $e^{G_i-G_j}>1$ 的形式静默参与计算，不会 NaN、不会越界，只是结果错。这是本 kernel 最危险的一处"约定式正确"。
  真正被写成下三角的只有两个缓冲：`chunkScoresFp32`（:581 只写 `jj<i`，:586 写对角 1，上三角保持 0 —— `ComputeRecursiveAttn` 的注释 :316 声明的正是这个不变量）和覆盖后的 `decayMaskFp32` 下三角部分。
- **exp 的溢出/下溢隐患**，四条：
  1. `Exp` 的输入 $G_i$ 本应 $\le 0$（g 是 log 域衰减）。kernel 与 tiling **都不校验 g 的符号**：若 g>0（误用/上游 bug），`expGCumFp32` 可达 $e^{64\max g}$；FP32 上限约 $e^{88.72}$，超出即 `inf`，随后 `Muls(..., gExp, ...)`（:624）把 inf 带进 K_cd，再经 `Axpy` 污染 S 与输出，且 inf×0 会产生 NaN 并沿"×1.0 刷新"一路写进 GM。
  2. 反向（很负）时 $e^{G_i}$ 下溢为 0，数学上正确（完全遗忘），但 `decayMaskFp32` 的上三角会同时出现 `inf`（$G_i-G_j$ 很正），虽然不读，`Exp` 的硬件实现仍会写 `inf` 进 UB —— 排查"矩阵里有 inf 但结果对"时不要误判。
  3. `length = cs` 而非 `chunkLen`：尾块残留区（上一 chunk 的 $G$ 值）也会被 exp。残留 $G$ 一定比当前 chunk 的更负（单调性沿 token 累积），所以最坏是更严重的下溢 ⇒ 0，安全；但如果上游给的 g 变号，这条保护就不存在。
  4. `Sub(deltaFp32, deltaFp32, gCumsumFp32, cs)` 要求 `deltaFp32 ≥ cs` 元素：`deltaSize = max(dotProductSize, vStepA) ≥ cs`（:186-187，`dotProductSize = max(stateStrideK_, cs)`）恒成立 ⇒ 缓冲复用是安全的，这个不等式是它唯一的守卫。

**可优化点（读后续 PR 时对照）**：:523-531 的 64 次"广播-减-exp"完全可以展平成一次 4096 元素的 `Sub` + 一次 4096 元素 `Exp`（`decayMaskFp32` 自身容量就是 4096）。作者选按行是为了不占用第二块 16KB UB（`deltaFp32` 只有 128 元素）。

## 11. ComputeAttnMatrix：两次 O(n²) 点积 + 一次递归 + 一次原地覆盖

锚点：chunk_gated_delta_rule.h:576-616

```cpp
  // Phase 4: attn = -((k_beta @ K^T) * decay_mask) (lower tri), recursive accumulation, identity
  // diagonal; then attn_i = (Q @ K^T) * decay_mask overwrites decayMaskFp32 (lower tri + diag). 
  __aicore__ inline void ComputeAttnMatrix(uint64_t qkHead, int32_t t_start, uint32_t chunkLen) {
    uint32_t cs = chunkSize_;
    for (uint32_t i = 1; i < chunkLen; i++) {
      for (uint32_t jj = 0; jj < i; jj++) {
        float dot = DotFp32(kCumdecayFp32[i * alignK_], chunkKFp32[jj * alignK_], realK_);
        chunkScoresFp32.SetValue(i * cs + jj, -dot * decayMaskFp32.GetValue(i * cs + jj));
      }
    }
    ComputeRecursiveAttn(chunkScoresFp32, chunkLen, cs);
    for (uint32_t i = 0; i < chunkLen; i++) {
      chunkScoresFp32.SetValue(i * cs + i, 1.0f);
    }
    if (CanCacheAttnQuery(chunkLen)) {
      for (uint32_t i = 0; i < chunkLen; i++) {
        LocalTensor<float> queryRow = chunkAttnOutFp32[i * alignK_];
        for (uint32_t jj = 0; jj <= i; jj++) {
          float dot = DotFp32(queryRow, chunkKFp32[jj * alignK_], realK_);
          float decay = decayMaskFp32.GetValue(i * cs + jj);
          decayMaskFp32.SetValue(i * cs + jj, dot * decay);
        }
      }
    } else {
      for (uint32_t i = 0; i < chunkLen; i++) {
        int32_t t_i = t_start + i;
        uint64_t qkOff_i = (static_cast<uint64_t>(t_i) * NK_ + qkHead) * realK_;
        for (uint32_t d = 0; d < realK_; d++) {
          deltaFp32.SetValue(d, static_cast<float>(queryGm_.GetValue(qkOff_i + d)) * scale_);
        }
        TQueSync<PIPE_S, PIPE_V> querySync;
        querySync.SetFlag(0);
        querySync.WaitFlag(0);
        for (uint32_t jj = 0; jj <= i; jj++) {
          float dot = DotFp32(deltaFp32, chunkKFp32[jj * alignK_], realK_);
          float decay = decayMaskFp32.GetValue(i * cs + jj);
          decayMaskFp32.SetValue(i * cs + jj, dot * decay);
        }
      }
    }
  }

 
```

四段职责：

1. **:578-583 直接项 $B_{ij}$**。$B_{ij} = -(k_\beta^{(i)} \cdot k^{(j)})\,e^{G_i-G_j}$，其中 $k_\beta^{(i)}$ 就是 `kCumdecayFp32` 第 i 行（Phase 2 的产物，身份 `β_i k_i`）。取负在标量侧做（`-dot * decay`）。**行 0 不生成**（`i` 从 1 起），因为第 0 行没有 $j<i$，其值将只由 :586 置 1。
2. **:584 递归修正**（04 篇 §7）：把严格下三角 $B$ 变成 $A=(I-B)^{-1}$。这是"用递推替代求逆"的唯一实现点。
3. **:585-587 单位对角**：`A[i][i]=1`，与 :584 之前的 0 对角合起来构成 $(I-B)^{-1}$ 的单位下三角结构。注意它排在递归**之后**：递归过程要求对角保持 0（`Axpy` 的前缀长度 `k` 天然不碰下标 ≥ k，但 :320 的系数缓存会读 `buf[i*ld+k]`，若对角已是 1 就会把 $B_{ii}=1$ 当系数用）——顺序不可调换。
4. **:588-613 QK 注意力并原地改写 `decayMaskFp32`**：$[i][j] \leftarrow (q_i \cdot k_j)\,e^{G_i-G_j}$（快路径里 $q_i$ 已含 scale；慢路径 :602 显式乘 `scale_`）。此后 :838 读到的 `decayMaskFp32` 身份已是 QK 矩阵。**读改写都在标量侧**（:593-594、:609-610），同一线程内顺序确定，无竞争。

其它要点：

- :581 与 :593-594 都读 `decayMaskFp32`，但**用途不同**：前者读的是纯 decay $e^{G_i-G_j}$，后者读后立刻覆盖成 QK 矩阵。同一份 decay 被用两次（A 的直接项 + QK 的权重），所以覆盖必须排在 :578-583 之后 —— 这就是"用完即毁"的准确表述：**毁点在 Phase 4 第四段，而不是 Phase 3 之后**。
- :580/:592 传的是 `LocalTensor` 行视图（`kCumdecayFp32[i*alignK_]`，`operator[]` 按元素偏移返回同类型视图），零拷贝；:590 亦然。这三处是 `LocalTensor` 作为"带基址的视图值类型"的典型用法。
- 慢路径 :601-603 把 GM 的 Q 行**逐元素乘 scale 后写进 `deltaFp32`**（容量 `deltaSize ≥ stateStrideK_ ≥ realK_` ✓），:604-606 的 `TQueSync<PIPE_S,PIPE_V>` 是**真正必需**的（标量写 UB → :608 `Mul` 向量读 UB）。但对象声明在 i 循环**内部**：每行重新构造/析构一个同步对象，比 §7 的循环外声明多 64 次开销，语义完全相同。两处写法不一致，属可统一的小瑕疵。
- :608 的 `DotFp32(deltaFp32, ...)`：`lhs` 参数是 `deltaFp32`，而 `DotFp32` 内部 :290 会把它和 `rhs` 的积写进 `dotProductFp32`（另一块缓冲），所以 `deltaFp32` 不会被归约覆盖 ⇒ 一行 Q 可以连续和 i+1 个 K 行做点积。这是 `deltaFp32`/`dotProductFp32` 必须**分成两块**的原因（若在同一个缓冲里做 in-place Mul，第 2 个点积起就把第 1 个的输入踩掉了）。
- 快/慢路径互斥且都在函数内完成同一数学，所以 :614 之后无需任何"哪条路径"的状态传递。

## 12. ComputeKCumdecay：K_cd = A · diag(e^G) · K_beta

锚点：chunk_gated_delta_rule.h:617-648

```cpp
 // Phase 5: k_cumdecay = attn @ (k_beta * exp(g_cumsum)); result stored back into chunkKFp32.  
  __aicore__ inline void ComputeKCumdecay(uint32_t chunkLen) {
    uint32_t cs = chunkSize_;
    TQueSync<PIPE_S, PIPE_V> expValueSync;
    for (uint32_t i = 0; i < chunkLen; i++) {
      float gExp = expGCumFp32.GetValue(i);
      expValueSync.SetFlag(0);
      expValueSync.WaitFlag(0);
      Muls(kCumdecayFp32[i * alignK_], kCumdecayFp32[i * alignK_], gExp, realK_);
    }
    TQueSync<PIPE_V, PIPE_S> decaySync;
    decaySync.SetFlag(0);
    decaySync.WaitFlag(0);
    TQueSync<PIPE_S, PIPE_V> coefficientSync;
    for (uint32_t i = 0; i < chunkLen; i++) {
      LocalTensor<float> outRow = chunkKFp32[i * alignK_];
      Duplicate(outRow, 0.0f, realK_);
      PipeBarrier<PIPE_V>();
      for (uint32_t k = 0; k <= i; k++) {
        float score = chunkScoresFp32.GetValue(i * cs + k);
        coefficientSync.SetFlag(0);
        coefficientSync.WaitFlag(0);
        Axpy(outRow, kCumdecayFp32[k * alignK_], score, realK_);
        PipeBarrier<PIPE_V>();
      }
    }
    TQueSync<PIPE_V, PIPE_S> outputSync;
    outputSync.SetFlag(0);
    outputSync.WaitFlag(0);
  }
```

- 前半 :620-625：`kCumdecayFp32 ← kCumdecayFp32 · diag(e^{G_i})`，即 $K_\beta$ 每行乘自己的 $e^{G_i}$，**原地**（dst 与 src 同一行）。原地在此安全：`Muls` 是"读完一行再写同一行"的向量指令，同管道内自序，且 `PipeBarrier` 被块级 `decaySync`（:626-628）覆盖。
  `gExp` 从 `expGCumFp32` 标量读——它的可见性由 Phase 3 的 :520-522 V→S 点保证，而 :622-623 的 `expValueSync` 是 S→V 方向，**不能**替代它。这是一对常被读混的相邻同步：一进一出，方向不同、保护对象不同。
- :626-628 `decaySync`（V→S）：块级收口（与 :508-510 同形）。
- :629-641 后半是**标准软件 GEMV**：外层输出行 `i`，内层累加项 `k ≤ i`（下三角含对角），系数 `A[i][k]` 标量取，源行 `K'_beta[k]` 用 `Axpy` 累加。这是本 kernel 里矩阵乘的规范形态，06 篇的 Step 2/4/5/6/7 全是它的变体。
  - `k ≤ i` 的上界：$A$ 是单位下三角，$k>i$ 恒 0，跳过即省一半。
  - :632 `Duplicate(outRow, 0.0f, realK_)`：**必须先清零**，因为 `outRow` 是 `chunkKFp32` 的行，里面还躺着原始 K，而 `Axpy` 是"加"不是"写"。清零长度 `realK_` ⇒ 行 padding 保留原 K 的 padding（永远不被读，见 §5）。
  - :633 `PipeBarrier<PIPE_V>`：Duplicate 与随后第一条 Axpy 写同一行，同管道必须排空（否则 Axpy 可能读到未清零的行）。
  - :634-640：每次 `Axpy` 前一次标量 `GetValue`、后一次 `PipeBarrier<PIPE_V>` ⇒ $\frac{65\cdot64}{2} \approx 2080$ 条 Axpy、同样多的同步。与 `ComputeRecursiveAttn` 合计，K 侧每 chunk 约 4000 条 Axpy + 4096 次点积，**这就是"向量化基线"的延迟底账**（docs/PR-406 §7 ①）。
- :642-644 `outputSync`（V→S）：**这条不是保守装饰**。Phase 6 Step 4（:796）要用**标量** `GetValue` 读 `chunkKFp32`（此时身份已是 K_cd）。中间隔着 `PrepareAttnQueryCache`? 不——顺序是 Phase 5 → `ProcessVTiles` → `ProcessOneVTile` → Step1/2/3 → Step4，中间 Step 2 有 S→V 与 Step 3 的 DMA 事件，但**没有任何 V→S 点**，所以 :642-644 是 :796 那次标量读的唯一可见性来源。删掉它，K_cd 可能读到旧 K ⇒ 结果错但不崩。这是"必须存在"的一类跨函数同步，值得在改动时重点守。
- `chunkSize_` 在 :618 被取出成 `cs`，仅用于 :635 的行跨距（$A$ 的 `ld` 恒为 `chunkSize_`，与 `chunkLen` 无关）。
