## 2. `CopyL0CToUb`：封装本体

锚点：src/048d0427/op_kernel/chunk_gated_delta_rule.h:116-127

逐字（新增的全部 12 行）：

```cpp
  __aicore__ inline void CopyL0CToUb(LocalTensor<float> dst, LocalTensor<float> src,
                                     const DataCopyParams &copyParams,
                                     const DataCopyEnhancedParams &copyEnhanced) {
    event_t mToV = static_cast<event_t>(pipe_->FetchEventID(HardEvent::M_V));
    event_t vToM = static_cast<event_t>(pipe_->FetchEventID(HardEvent::V_M));
    SetFlag<HardEvent::M_V>(mToV);
    WaitFlag<HardEvent::M_V>(mToV);
    DataCopy(dst, src, copyParams, copyEnhanced);
    SetFlag<HardEvent::V_M>(vToM);
    WaitFlag<HardEvent::V_M>(vToM);
  }
```

位置：`Init`（:105-114）与 `SetGlobalTensors`（:128）之间 —— 放在所有 Cube 函数之前，纯工具函数。

三点对读代码最重要的结构事实：

1. 它**只新增事件，不删除任何东西**。8 处调用点其后仍保留原有的 `PipeBarrier<PIPE_ALL>()`
   （diff 里每处只改 1 行即可证明）。所以 !1174 是**纯加法**，不可能改变原有时序中"已经正确"的部分。
2. 形参是 `LocalTensor<float> dst, LocalTensor<float> src`，与 8 处调用实参 `cNz`（UB fp32）/
   `c1Local`（L0C fp32）严格同型。它不是"通用的 UB→UB 搬运"，签名本身就锁定了 **L0C→UB 这一个方向**。
3. 事件 ID 由 `pipe_->FetchEventID(...)` 向 pipe 申请，而非硬编码数字 ——
   与文件里封装之外的 **23 处** `FetchEventID` 用法同式（全文件共 25 处，覆盖 9 种事件类型：
   `V_MTE2` 6、`MTE2_V` 6、`V_MTE3` 5、`MTE3_MTE2` 2、`MTE3_V` 2、`MTE2_S`/`S_MTE2`/`M_V`/`V_M` 各 1）。
   `HardEvent::` 在全文件共出现 205 次，其中 65 次 `SetFlag` 直接用字面事件号 `0` ——
   那 65 次**全部**属于 `MTE2_MTE1`(23) / `MTE1_M`(22) / `M_MTE1`(20) 这三条五件套内部边；
   跨 UB/GM 的边以及本次新增的 M↔V 边一律走 `FetchEventID`。ID 取法的这条分界线在 §03 报告里展开。

## 4. `PipeBarrier<PIPE_ALL>` 挡不住什么

锚点：src/048d0427/op_kernel/chunk_gated_delta_rule.h:511-517；src/d0906c3e/op_kernel/chunk_gated_delta_rule.h:1822-1834

### 4.1 两种原语的语义差别

锚点：src/048d0427/op_kernel/chunk_gated_delta_rule.h:116-127、121、124；src/048d0427/op_kernel/chunk_gated_delta_rule.cpp:28；src/88d8b965/op_kernel/chunk_gated_delta_rule.h:499；src/d0906c3e/op_kernel/chunk_gated_delta_rule.h:1885-1897

| | `PipeBarrier<PIPE_ALL>()` | `SetFlag<H>` / `WaitFlag<H>`（H = `HardEvent::M_V` 等） |
|---|---|---|
| 表达的东西 | 本指令流上的一个**对齐点** | 一条**有名的跨管依赖**（源管→宿管） |
| 作用域 | 只治理"我这条流"前后下发的顺序 | 点名到具体管道对，别的管不受影响 |
| 能否表达"对端管已经退休" | **不能**：它不携带源→宿语义，M 管与 V 管各自独立流水 | 能：`WaitFlag` 阻塞到 `SetFlag` 点之前的源管工作真的执行完 |
| 方向性 | 无方向（全管对齐） | 有方向：`M_V` 只管 M→V，管不了 V→M |
| 代价 | 打断流水，最贵 | 一对事件寄存器操作，标量级 |
| 文件里用量 | `PIPE_ALL` 29 次、`PIPE_V` 92 次 | `FetchEventID` 25 处（23 处原有 + 本封装 2 处） |

两条**可在快照里复核**的证据支撑这个判断，不需要借助任何外部说法：

1. `src/048d0427/op_kernel/chunk_gated_delta_rule.cpp:28` 是
   `KERNEL_TASK_TYPE_DEFAULT(KERNEL_TYPE_AIC_ONLY);` —— Cube 与 Vector 的指令由同一条流下发，
   但**在各管上独立退休**。这种模式下"下发到哪"与"哪条管跑完了"是两件事，能表达后者的只有具名事件边。
2. 修复前那处代码里，栅栏的位置就不对。d0906c3e `ComputeVNewCube` 的原文顺序是：
   `:1885` 最后一条 `Mmad(c1Local, ...)` → `:1887-1888`
   `SetFlag<HardEvent::M_MTE1>(0); WaitFlag<HardEvent::M_MTE1>(0);` →
   `:1896` `DataCopy(cNz, c1Local, cCopyParams, cCopyEnhanced);` →
   `:1897` `PipeBarrier<PIPE_ALL>();` → `:1904-1906` NZ→ND 读回循环。
   也就是说：**Mmad 与 L0C→UB 复制之间只有 `M_MTE1` 这一对**（Cube↔L1 的完成点，语义是
   "Cube 腾出了 L1，MTE1 可以继续搬下一块"，完全不携带"VEC 可以来读 L0C"）；
   唯一的 `PIPE_ALL` 落在复制**之后**，治理的是"复制 → 读回"的本地顺序，而不是报错点名的 L0C 读写冲突。
   `CopyL0CToUb` 补的正是复制**前**那条 `M_V` 和复制**后**那条 `V_M`。

事件才是唯一携带"完成 + 方向"语义的原语：`SetFlag<HardEvent::M_V>` 把 M 管当下的完成点登记成事件，
`WaitFlag<HardEvent::M_V>` 让 V 侧在该事件上阻塞。方向必须成对：
M→V（"我写完了 L0C，你可以来读"）与 V→M（"我读完了，下一轮 Mmad 才能覆写"）
是两条**不同的**事件边，`HardEvent::M_V` 与 `HardEvent::V_M`，不能互相代用。

### 4.2 竞争时序（以 docs 用的同一个函数 `ComputeVNewCube` 为例，行号实测）

锚点：src/d0906c3e/op_kernel/chunk_gated_delta_rule.h:1822、1843、1896、1905、1910

d0906c3e 中该函数起于 :1822，五件套 → L0C 落地 → V 侧读取的顺序是：

```
V    : StageHalf(stateInFp32, bStageGm, kBElements)          // :1843
MTE2 : Nd2Nz DataCopy a1Local <- aStageGm
MTE1 : LoadData  a2Local <- a1Local
M    : Mmad(c1Local <- a2 x b2, init = true)                    (1)
M    : Mmad(c1Local <- ... , init = false)  续累同一 L0C        (2)
M    : DataCopy(cNz, c1Local, ..., BLOCK_MODE_MATRIX)  L0C->UB   (3)  :1896
V    : for (row) DataCopy(chunkVFp32[row*kMatmulN], cNz[row*16], nzToNd)   (4)  :1905
V    : Add(chunkVFp32, chunkVFp32, chunkAttnOutFp32, kCElements)            (5)  :1910
```

（(3) 与 (4) 的原文，逐字：`src/d0906c3e/...:1896` 的 `DataCopy(cNz, c1Local, cCopyParams, cCopyEnhanced);`
与 `:1905` 的 `DataCopy(chunkVFp32[row * kMatmulN], cNz[row * 16], nzToNdParams);`；
中间只夹着一个 `PipeBarrier<PIPE_ALL>();`。同一处在修复前快照 88d8b965 是 :1897 / :1906，
在修复后 048d0427 是 :1909 / :1918。）

竞争在 **(3) 与 (4) 之间**，且 (3) 与 (2) 之间也有：
- (3) 未搬完，(4) 就读 `cNz` → V 读 L0C 数据通路 / CUBE 写 L0C 撞在同一地址；
- (2) 的 Mmad 还在往 `c1Local` 累加，(3) 已经开始把它往外读 → 同一 L0C 地址同时被 VEC 读、被 CUBE 写。

`CopyL0CToUb` 的两个事件对正好各自堵住这两条：搬前的 `M_V` 让"上一轮 Mmad 写完 L0C"成为
"VEC 读 L0C"的前置条件；搬后的 `V_M` 让"本轮 VEC 读完 L0C / UB"成为"下一轮 Mmad 再写 L0C"的前置条件。

### 4.3 为什么 !1108 时代不存在这条边，因而没暴露

锚点：src/048d0427/op_kernel/chunk_gated_delta_rule.h:342、413、540、547、660、883、909、950、1017、1169、1201、1220、1243、1403、1530、1541、2149、2411（全部 18 处 `TQueSync`）

`!1108` 的世界只有 V / S / MTE2 / MTE3 四条管，同步模式（`TQueSync<PIPE_S,PIPE_V>`、
`V_MTE2`/`MTE2_V`/`V_MTE3`）已足够，**根本没有 M 管**。
本文件里那 18 处 `TQueSync` 全是 `PIPE_S↔PIPE_V` 方向（`TQueSync<PIPE_S,PIPE_V>` 6 处 +
`TQueSync<PIPE_V,PIPE_S>` 12 处），**没有一处涉及 M 管或 L0C**。
!1135 上 AIC 后新增的 M 管与 L0C 引入了新的跨管边，但 L0C→UB 的写法沿用了 !1108 时代
"UB 上写读 + `PIPE_ALL`"的惯性 —— **换硬件单元 = 新增同步边**，这是移植类 bug 的通用形态。
TQue 的同步语义锚在队列位置（VECIN/VECOUT，V↔MTE），生产者/消费者是 V 管与 MTE 管，
它压根不感知 M 管，所以此处无法用队列替代裸事件。

## 5. 为什么症状是崩溃而不是算错

锚点：docs/PR-1135-d0906c3e/10-Commit演进史.md:349-351

真机抓到的硬件报错，一字不差（出处 `docs/PR-1135-d0906c3e/10-Commit演进史.md:349-351`）：

```text
error code = 0x100000000020000, errorStr: L0C read/write conflict
(vec read operation or cube write operation). VEC read/write L0C and
cube read/write L0C addresses are the same.
```

这条报错本身就是机理证据，三个信息点全都在里面：

1. **冲突发生在 L0C 上**，不是 UB。UB 是普通 SRAM、有读写口仲裁，同址读写最坏算错；
   L0C 是 Cube 的累加器存储，**不做 VEC/CUBE 同址仲裁**，一旦撞上去就直接抛异常 →
   这就是"症状是 exception 而不是数值偏差"的直接原因。
2. 括号里点名了两造：`vec read operation` **或** `cube write operation`
   —— 与 §4.2 的 (3)V 读 L0C / (2)CUBE 写 L0C 一一对应，不是推测。
3. `addresses are the same`：判据是**地址相等**，不是数据依赖。所以只要两条指令的 L0C 地址重叠即为非法，
   与时序裕量共同决定"撞不撞得上"——这解释了为什么同一个 kernel 会时崩时不崩。

外层表现：`runtime result = 507015`（aicore exception）、
`fault kernel_name=ChunkGatedDeltaRule_...`（直接指认肇事 kernel），
`npu-smi` 前后健康、重启自愈（出处 docs/PR-1135-d0906c3e/10-Commit演进史.md:346、
docs/PR-1174-048d0427/02-实验复现.md:69-72）。
另需注意崩溃会污染设备：a9c66ddb 首跑出现过"1 failed + **2 errors**"，
后两条 error 是崩溃后设备脏导致下一条用例的数据生成算子报错，不是三个独立 bug
（出处 docs/PR-1135-d0906c3e/10-Commit演进史.md:340-342）。

**对照 §01 那一类 bug 的表征**：!1158 是 UB 内的地址别名，硬件不管，所以静默算错；
!1174 是 L0C 上的跨管同址读写，硬件硬拦，所以间歇崩溃。同一个"重叠"关键词，
一个走数值通道、一个走异常通道，这是两类 bug 最根本的分野。

## 6. 为什么长序列才崩

锚点：src/048d0427/op_kernel/chunk_gated_delta_rule.h:511-517（竞争窗口在稳态热循环里的位置）

竞争是**时序窗口问题**：崩溃 ⟺ V 管执行到 (4) 的时刻早于 M 管完成 (3) 的时刻。
平时不炸，是因为 (3) 的完成延迟通常短于 V 管从发射 (4) 到真正读之间要做的准备工作 —— **靠裕量掩盖**。
裕量被吃光的两个条件，都随负载单调变薄：

1. **chunk 数 × head 数增加** → `ProcessOneVTile` 里的 Cube 往返次数线性增加
   （表 #2/#3/#5/#6/#7/#8 所在函数几乎每个 chunk 都要走一遍），
   连续多个 Cube 函数背靠背：V 管刚发完 (4)(5) 就被下一个函数调走，`cNz` 的读还悬着；
2. **长序列 → 流水被填满**：V 管在两次 Cube 往返之间的"闲活"（准备下一 stage 的 GM 暂存）
   被 !1135 的双 slot 流水优化越压越薄，可掩盖延迟的空隙随之消失。

实测印证（出处与性质标明）：
`2×8×512×128×128`（8 chunks × 8 heads × 满流水）约 **1/3 概率**崩溃，
单跑 3 次为 pass/crash/pass；`1×16×128`（2 chunks）**从不崩**
（docs/PR-1174-048d0427/01-L0C同步与裸Cube编程.md:44、PLAN.md:106，蓝区 310P3，2026-09-08）。
后续中间 commit 矩阵又给出两个互补的观察：`long_t2048` 跑 3 次 pass/crash/pass、
`long_t512_batch2` 2 次 crash/pass（docs/PR-1135-d0906c3e/10-Commit演进史.md:344-345）。
**T 越长崩得越频繁**，与"裕量变薄"的模型同向。

另一条独立的加固证据（同一 bug 谱系，非本文推演）：崩溃 kernel 名后缀随 tilingKey 个数变化
（3 桶版 `_2`、4 桶版 `_3`），但崩溃 shape 簇（dk=128 长序列）、概率量级（~1/3）、
硬件机理（L0C 读写冲突）在 a9c66ddb → 69300ffc → d0906c3e 整条分支上完全一致
（docs/PR-1135-d0906c3e/02-实验复现.md:222-226）。
这排除了"某个中间 commit新引入竞争"的解释，也与本文 §3.2 的"M↔V 边计数一直为 0"完全吻合。

## 7. 按不变式修复，而不是按症状打补丁

锚点：src/048d0427/op_kernel/chunk_gated_delta_rule.h:511、1183、1298、1734、1823、1909、2058、2271

**不变式**：任何"由 Cube 侧写 L0C、随后被 Vector 侧读"的搬运，两侧必须各有一道 M↔V 事件栅栏。

论证链条，每一环都是实查：

1. 竞争是概率性的（§4、§6）。一次崩溃日志只能指认**发生崩溃的那一个 kernel 实例**，
   无法指认"只有这一处有窗口"。测试能覆盖的 shape 簇是有限的：
   实测崩溃集中在 `dk=128` 长序列（docs/PR-1135-d0906c3e/02-实验复现.md:225），
   而表里 8 处分布在 8 个不同函数、由不同 fast-path 判定进入 ——
   慢路径函数（#5 `ComputeValueNewCube`、#6 `ComputeVNewCube`）在快路径可用的 shape 下**根本不被调用**，
   崩溃日志永远不可能指认它们。
2. 逐点数竞争窗口，8 处都在，且**宽度不同**（`grep -n 'Mmad('` 实测 21 处的分布）：
   - #1 `MatmulBlockFp32Compensated`：L0C 目的由 `MmadMatmulBlock`（:452-459）里的**单条** `Mmad`
     按 `init` 开关续累（:456 的 `init` 是形参），一次调用内被反复累加多次再落地 —— 窗口中等；
   - #4 `ComputeValueAndVNewCube`：函数体内有 **4 次 Mmad**（:1673、1686、1713、1726，
     两组 `kAttnK` / `kStateK` 链共享同一 `c1Local`）却只有 **1 处** L0C 落地（:1734）——
     **紧邻复用 + 落地次数少于累加次数，竞争窗口最长**，与 docs 的判断一致；
   - #7 `ComputeOutputCube`：同样 4 次 Mmad（:1994、2007、2037、2050）对 1 处落地（:2058），结构与 #4 同构；
   - #2 `CopyAttnCubeResult`：本体只 1 处落地（:1183），但它被 `ComputeAttnProductsCube`
     调用 **2 次**（:1127 目的 `chunkScoresFp32`、:1156 目的 `chunkAttnOutFp32`），
     对应 attn 的两个矩阵 —— 单 chunk 内该封装执行 2 次；
   - #8 `ComputeStateUpdateCube`：落地在 m-tile **循环体内**（:2271，6 空格缩进），
     M-tile 越多则触发次数越多，且 `cNz` 还在分支里换绑到 `tmpBuff` 偏移 0（:2266），
     是 8 处中缓冲身份最不稳定的一个。
3. 因此"只修测试崩的那一处"会在下一个 shape / 下一个 CANN 版本上以同样的形态复发；
   8 处一次性替换的成本只是 8 行，收益是不变量成立。
4. **可验证性**：正因为做成了不变式，§3.2 的三条 `grep` 才能作为验收判据
   （残留裸搬 0、L0C 分配 8 ↔ 调用 8、事件边 0→3+3）。
   按症状打补丁的修复给不出这种可复跑的完备性证明 —— 这是两种修法的工程差别。

顺带一条对 review 的可操作建议（从 §3.2 的"事件边为 0"直接得出）：
读任何 AIC 算子代码，先 `grep -c 'Mmad('` 与 `grep -c 'HardEvent::M_V\|HardEvent::V_M'` 对比 ——
前者远大于 0 而后者为 0，就是同一形态的缺陷。

## 8. 为什么修复零性能开销

锚点：src/048d0427/op_kernel/chunk_gated_delta_rule.h:116-127（封装体即全部新增工作）

实测（出处 docs/PR-1174-048d0427/02-实验复现.md:80-87，与 PLAN.md:113 一致；
"修复前"列即 d0906c3e / !1135，蓝区 310P3、CANN 8.3.RC1，2026-09-08）：

| shape | !1135 ms | 048d0427 ms |
|---|---|---|
| 1×8×64×64×64 | 0.928 | 0.858 |
| 1×16×128×128×128 | 1.151 | 1.141 |
| 1×1×128×128×256 | 0.831 | 0.819 |
| 2×8×512×128×128 | 4.355 | 4.373 |
| 1×16×1024×128×128 | 8.746 | 8.757 |
| 1×16×2048×128×128 | 18.954 | 17.357 |

6 个 shape 全部落在 ±1.5% 内（最大相对变化出现在 t2048：18.954→17.357，方向还是变快）。
正确性侧：d0906c3e 12 passed / 1 failed → 048d0427 **15 passed / 0 failed / 13 skipped**；
`long_t512_batch2` 修复后连续通过（4.363 / 4.376 ms），无崩溃
（docs/PR-1174-048d0427/02-实验复现.md:76、89，PLAN.md:112、114）。
本文未复核这些数字，它们来自上述文档记录的蓝区实验。
**注意一个二手数字的自相矛盾**：同为 d0906c3e 的 6 shape 性能，
PLAN.md:96-103（2026-09-08）给 0.928/1.151/0.831/4.355/8.746/18.954，
而 PLAN.md 中间 commit 矩阵（2026-09-14 重跑，:132-138）给 0.869/1.132/0.794/4.340/8.737/~17.4。
两个时点相差可达 6%（0.928 vs 0.869），**量级与"零开销"结论同向，但引用时必须带时点**。

零开销的机理（两条，都可在 §2 的代码上直接验证）：

1. **栅栏等待的事件本来就要发生**。V 管反正必须等 `cNz` 搬完才能算 NZ→ND；
   M 管反正必须等上一轮 Mmad 写完 L0C 才能安全读它。`SetFlag/WaitFlag` 只是把这两个"本来存在的依赖"
   从"靠时序运气满足"改成"靠硬件事件满足"，**没有引入任何新的等待关系**。
2. **新增指令的代价是标量级的**。封装里除了那条原有 `DataCopy` 只多了 2 次 `FetchEventID` +
   2 对 `SetFlag/WaitFlag`，都是寄存器/事件号操作；被等待的对象 `Mmad` 是微秒级。
   更关键的是它**没有**用 `PipeBarrier<PIPE_ALL>`：文件里 29 次 `PIPE_ALL` 才是打断流水的贵原语，
   而这次修复刻意选择了方向明确的事件（并且把 `PIPE_ALL` 原样留着），
   用最小约束换正确性 —— 这也解释了为什么它连"变慢一点点"都几乎没有。

反面判据（本 PR 给出的可迁移结论）：**代价高昂的栅栏是加在不会自然发生的依赖上的那种**。
比如把两个并无数据依赖的 Cube 调用用事件串起来，才是真实降速。
所以"加栅栏的判据是数据依赖，不是保守程度"。
