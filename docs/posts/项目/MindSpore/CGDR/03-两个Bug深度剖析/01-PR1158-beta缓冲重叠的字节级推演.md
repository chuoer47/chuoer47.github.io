### 2.1 三个常量与类型

锚点：src/88d8b965/op_kernel/chunk_gated_delta_rule.h:35-37


`BLOCK_BYTES / sizeof(T)` 这个式子在文件里本来就是官方分块模型（:46 `int64_t numPerBlock = BLOCK_BYTES / sizeof(T);`）。
`inType` 是模板形参（:74 `template <typename inType, typename outType, uint32_t kSpecializedDk>`），

### 2.2 beta 板布局与 stride 关系

锚点：src/88d8b965/op_kernel/chunk_gated_delta_rule.h:359-362、780-787、813

- GM 侧 beta 是 `[T, NV]` 的 fp16 板。标量兜底路径印证行主序：
  `LoadBeta`（:359-362）内 `betaGm_.GetValue(t * NV_ + head_i)`。
- DMA 搬的是**整板一块**：`betaGm_[t_start * NV_]` 起、`slabElements = chunkLen * NV_` 个 fp16，
  即 `[chunkLen][NV_]` 连续区域，共 `2·chunkLen·NV_` 字节。
- Gather 的列抽取靠字节偏移完成，见 `BuildCoefficientOffsets`：

锚点：88d8b965/op_kernel/chunk_gated_delta_rule.h:780-787（该函数体在 !1174 中一字未改，在 048d0427 快照里整体后移 12 行至 792-799）

```cpp
  __aicore__ inline void BuildCoefficientOffsets(LocalTensor<uint32_t> offsets, uint32_t chunkLen) {
    LocalTensor<int32_t> signedOffsets = offsets.template ReinterpretCast<int32_t>();
    CreateVecIndex<int32_t>(signedOffsets, 0, chunkLen);
    PipeBarrier<PIPE_V>();
    Muls(signedOffsets, signedOffsets, static_cast<int32_t>(NV_ * sizeof(float)), chunkLen);
    PipeBarrier<PIPE_V>();
  }
```

  偏移 = `i · NV_ · 4` 字节，`srcIdxStrideBytes = head_i · 4` —— 也就是说 Cast 之后的 `chunkVFp32`
  被当作 `[chunkLen][NV_]` 的 **fp32** 板来抽列，行 stride = `NV_·4` 字节。

因此元素下标 `i`（平铺，0-based）与 `(t, h)` 的对应是 `i = t·NV_ + h`。这个对应是 §3 全部算术的基础。

### 2.3 快速路径的进入条件（实查 host 侧参数）

锚点：src/88d8b965/op_kernel/chunk_gated_delta_rule.h:817、82、135；src/88d8b965/op_host/chunk_gated_delta_rule_tiling.cpp:32、110、171、299

`canUseBetaDma` 两项条件在真实 shape 下几乎恒成立：

- `slabElements · 2 % 32 == 0` ⟺ `chunkLen·NV_ % 16 == 0`。`chunkSize_ = 64`
  （锚点：src/88d8b965/op_host/chunk_gated_delta_rule_tiling.cpp:32 `constexpr uint32_t kDefaultChunkSize = 64;`），
  `64·NV_ % 16 == 0` 恒成立。
- `slabElements ≤ slabCapacity` ⟺ `chunkLen·NV_ ≤ chunkSize_·vStepAligned_`。
  `vStepAligned_ = Ceil(vStep_, 8)·8 ≥ 8`（锚点：src/88d8b965/op_kernel/chunk_gated_delta_rule.h:135），
  故整 chunk（`chunkLen == 64`）时条件退化为 `NV_ ≤ vStepAligned_`。

`NV_ = tilingData->hv`（锚点：src/88d8b965/op_kernel/chunk_gated_delta_rule.h:82），
`hv` 取自 value 分支的头维（锚点：src/88d8b965/op_host/chunk_gated_delta_rule_tiling.cpp:110 `dims.hv = vDims.GetDim(kDimH);`），

## 3. 字节级覆盖过程推演

锚点：src/d0906c3e/op_kernel/chunk_gated_delta_rule.h:819-831

### 3.1 起点：源和目的是同一个地址

修复前那个 `betaLocal` 不是别人的缓冲，它**就是 `Cast` 的目的缓冲本身**：`src/d0906c3e/` 的 :819 逐字为
`LocalTensor<inType> betaLocal = chunkVFp32.template ReinterpretCast<inType>();`
（6 空格缩进，即 §1 那段 diff 的 `<` 行；!1158 换掉的正是这条语句的源缓冲名）。于是同一个 `betaLocal`
在 d0906c3e 的 :823 是 DMA 的写入目的、在 :827 又是 Cast 的源，而 :827 的目的还是 `chunkVFp32` 自己。
DMA 与 Cast 这两条指令修复前后逐字节相同，只是被上面新增的那行注释整体推后 1 行，在 88d8b965 里是 :824 与 :828；
逐字见 88d8b965/op_kernel/chunk_gated_delta_rule.h:824-828：

```cpp
      DataCopy(betaLocal, betaGm_[static_cast<uint64_t>(t_start) * NV_], slabElements);
      ...
      Cast(chunkVFp32, betaLocal, RoundMode::CAST_NONE, slabElements);
```

`ReinterpretCast` 只换元素类型解释、不换基址。于是 `betaLocal` 与 `chunkVFp32` **基址相同**：
fp16 视图占据该地址起的前 `2·slabElements` 字节，fp32 视图占据前 `4·slabElements` 字节。
`Cast` 的 `dst` 是 fp32 视图、`src` 是 fp16 视图 —— **原地加宽**。

### 3.2 repeat 窗口表

锚点：src/d0906c3e/op_kernel/chunk_gated_delta_rule.h:827、35-37

设 `R` 为 repeat 序号（0-based）。Vector 管一条 Cast 指令按 32B 目的块推进，每 repeat 产出 8 个 fp32、消耗 8 个 fp16：

| repeat `R` | 读窗口（fp16 源，字节） | 读元素 | 写窗口（fp32 目的，字节） | 写元素 | 与更早写区间的关系 |
|---|---|---|---|---|---|
| 0 | `[0, 16)` | 0..7 | `[0, 32)` | 0..7 | 无（首个） |
| 1 | `[16, 32)` | 8..15 | `[32, 64)` | 8..15 | 读区间 ⊂ R0 写的 `[0,32)` ✗ |
| 2 | `[32, 48)` | 16..23 | `[64, 96)` | 16..23 | 读区间 ⊂ `[0,64)` ✗ |
| `R` | `[16R, 16R+16)` | `8R..8R+7` | `[32R, 32R+32)` | `8R..8R+7` | 前 R 个 repeat 已连续写出 `[0, 32R)` |

一般式（读区间完全落入已写出区间 ⟸ 读区间右端 ≤ 已写区间的右端点）：

```
   16R + 16 ≤ 32R        ⟺   16 ≤ 16R   ⟺   R ≥ 1
```

即**从第 2 个 repeat（`R = 1`）起，读窗口整体落在前面所有 repeat 已经写过的字节里**，
不是"部分相交"而是"完全被覆盖"。写窗口比读窗口宽 2 倍、且向前多延伸 16B，这多出来的 16B
正好吃掉下一个 repeat 的读窗口。

### 3.3 幸存集合与"8"的算术

锚点：src/d0906c3e/op_kernel/chunk_gated_delta_rule.h:35-37、46

幸存 ⟺ `R = 0` ⟺ 平铺元素 `i ∈ [0, 8)`。

`8` 的来源是 **32B / 4B**，不是 32B / 2B：

```
   每 repeat 产出元素数 = BLOCK_BYTES / sizeof(目的类型) = 32 / 4 = 8
```

理由：repeat 的推进节拍由**目的（写）侧**的 32B 块决定，一个 32B 目的块只装得下 8 个 fp32，
因此这条 Cast 每 repeat 只消费 8 个 fp16（= 16B 源）。源侧的 16B 块数（`FP16_NUM_PER_BLOCK = 16`）
描述的是"32B 里装几个 fp16"，不是"一个 repeat 消费几个 fp16"。
两个常量并排写在 :35-37 正是这层对照：`16 = 32/2`、`8 = 32/4`，**决定损坏边界的是后者**。

### 3.4 从"前 8 个元素"到"(t,h) 平面"

锚点：src/d0906c3e/op_kernel/chunk_gated_delta_rule.h:813、823、831

代回 `i = t·NV_ + h`，损坏集合与幸存集合为：

```
   幸存： t·NV_ + h < 8
   损坏： t·NV_ + h ≥ 8
```

按 `NV_`（即 `hv`）展开：

| `NV_` | 幸存的 `(t,h)` | 损坏范围 |
|---|---|---|
| 16 | `(0, 0..7)` 共 8 个 | `(0, 8..15)` + 所有 `t ≥ 1` |
| 8 | `(0, 0..7)` 共 8 个（= 第 0 行整行） | 所有 `t ≥ 1`，即 7/8 的板 |
| 4 | `(0, 0..3)`、`(1, 0..3)` 共 8 个 | 所有 `t ≥ 2` |
| 2 | `(0..3, h)` 共 8 个 | 所有 `t ≥ 4` |

`NV_ ≥ 8` 是 GQA/MHA 的现实区间，于是：

- **"head 序号 ≥8 的列全变垃圾"成立**（第 0 行的 `h ≥ 8` 直接落在损坏集）；
- 但它只是损坏集的一部分。更强的结论是：**只要走 DMA 快速路径且 `chunkLen ≥ 2`，`t ≥ 1` 的 beta 全部损坏**，
  与 head 数宽窄无关。docs 的"窄 shape 不受影响"这一条不成立，见 §8。

### 3.5 为什么单条指令内部不报错

锚点：src/d0906c3e/op_kernel/chunk_gated_delta_rule.h:827；src/d0906c3e/op_kernel/chunk_gated_delta_rule.h:35-37

Cast 是流式执行的：每 32B 块读入、运算、写出，块间顺序推进，硬件不知道也不需要知道源与目的在内存上相交。
这与 §2 的算术合起来构成一条硬约束：**加宽变换的原地执行在字节计数上就不可行**
（`n` 个源元素 = `2n` 字节，`n` 个目的元素 = `4n` 字节，目的区间必然超出源区间一倍），与具体调度无关。
重叠判定是程序员的责任 —— 这正是 AscendC 与普通 C++（`std::transform` 原地跑没问题）的语义差别之一。

一个必须诚实交代的不确定性：上表假设"repeat `R` 的读发生在 repeat `R-1` 的写之后"，即读/写按 repeat 严格串行。
真实 V 管可能带一级以上的预取（读 `R+1` 与写 `R` 重叠），那会把幸存前缀从 8 个元素推大一点（16、24……），
但**不会改变"只有常数级前缀幸存"这个量级结论**，也不会改变修复的正确性 —— 修复消除了别名本身。
快照无法回答预取深度，本文不猜；能回答它的只有 docs/PR-1158-88d8b965/02-实验复现.md §4 的 revert 实验。

## 4. 为什么 !1135 自带的测试没拦住

锚点：src/88d8b965/op_kernel/chunk_gated_delta_rule.h:834-838（else 分支，即被绕过的那条）

可复核的三点：

1. **存在两条语义等价的路径**。`canUseBetaDma` 为假时走 `for` 循环 `LoadBeta(t_start+i, head_i)` 标量逐元素读（:834-838），
   这条路径**永不触发 bug**。任何让护栏判假的 shape（例如 `NV_ > vStepAligned_`，见 §2.3）都会绕开损坏区，
   产生"同样的代码、有些 shape 对、有些 shape 错"的表象 —— 这正是 shape 相关静默错误的典型结构。
2. **触发条件不在测试断言里**。测试断言的是输出张量的 cosine/nrmse，而 bug 的作用点是**中间 UB 缓冲的地址别名**。
   别名不会改变任何静态可见的量（编译通过、shape 正确、内存不越界），只会污染数值。
3. **损坏是"部分列/部分行"而非"全体"**。§3.4 表明损坏集在 `(t,h)` 平面上是有结构的子集，
   随机小 shape + 宽容差下，被污染列的贡献可以被衰减与归一化稀释；要稳定暴露它，
   必须让 **head 维本身成为被测变量**。

### 5.2 下一个写者

锚点：88d8b965/op_kernel/chunk_gated_delta_rule.h:950-962

```cpp
  // chunkAttnOutFp32 is unused until V-tile processing. When it can hold a
  // full Q chunk, reuse chunkVFp32 as FP16 staging and cache Q*scale once for
  // the attention QK dot products.
  __aicore__ inline void PrepareAttnQueryCache(uint64_t qkHead, int32_t t_start, uint32_t chunkLen) {
    if (!CanCacheAttnQuery(chunkLen)) {
      return;
    }
    LocalTensor<inType> queryLocal = chunkVFp32.template ReinterpretCast<inType>();
    uint64_t qkOff = (static_cast<uint64_t>(t_start) * NK_ + qkHead) * realK_;
    LoadPaddedRows(chunkAttnOutFp32, queryLocal, queryGm_, qkOff, chunkLen, NK_ * realK_);
    Muls(chunkAttnOutFp32, chunkAttnOutFp32, scale_, chunkLen * alignK_);
    PipeBarrier<PIPE_V>();

```

`chunkAttnOutFp32` 在 :959 被 `LoadPaddedRows` **整块覆写**为 Q 缓存。

即在本函数（更早）到 `PrepareAttnQueryCache` 之间，它不承担语义。

### 5.3 上一个读者（为什么旧内容已经死了）

`chunkAttnOutFp32` 在 chunk 里的语义生命周期由 `ProcessOneVTile` 收尾。它是输出板，
末次消费者是 `WriteAttnTileToGm`：

锚点：88d8b965/op_kernel/chunk_gated_delta_rule.h:653-661

```cpp
  __aicore__ inline void WriteAttnTileToGm(int32_t t_start, uint32_t chunkLen, uint64_t head_i, uint32_t v_i,
                                           uint32_t curV, uint32_t avFp32) {
    uint32_t totalElem = chunkLen * avFp32;
    uint32_t alignedElem = Ceil(totalElem, FP32_NUM_PER_BLOCK) * FP32_NUM_PER_BLOCK;
    Muls(chunkAttnOutFp32, chunkAttnOutFp32, 1.0f, alignedElem);
    PipeBarrier<PIPE_V>();
    LocalTensor<outType> outLocal = stateOutQueue_.AllocTensor<outType>();
    Cast(outLocal, chunkAttnOutFp32, RoundMode::CAST_NONE, alignedElem);
    PipeBarrier<PIPE_V>();
```

:660 的 `Cast` 把 `chunkAttnOutFp32` **读完**，:661 的 `PipeBarrier<PIPE_V>()` 保证读已落地，
之后 `outLocal` 才入队交 MTE3 搬 GM。函数返回时 `chunkAttnOutFp32` 内容已无持有者。
而 `WriteAttnTileToGm` 在 `ProcessOneVTile` 里位置靠后（:1327，
在 `ComputeOutputCubeDispatch`/`AccumOutput` 之后、`UpdateAndWriteState`（:1328）之前），
`UpdateAndWriteState`（:2293 起）不再触碰 `chunkAttnOutFp32` ——
`grep -n 'chunkAttnOutFp32'` 在 88d8b965 共 38 处命中，函数体内最大行号 :2174；:2174 之后只剩 :2433 一条成员声明
（成员区从 :2411 的 `private:` 起），而 `UpdateAndWriteState` 的函数体是 :2293-2409，即该函数体内**零命中**。

多 V-tile 时的跨 tile 活性也不构成障碍：host/kernel 的 tmpBuff 注释明确写着
"multiple tiles: separate (scores must remain live across every tile)"（:150-152），
跨 tile 必须长命的是 `chunkScoresFp32`/`stateInFp32`；`chunkAttnOutFp32` 在每个 tile 的
`ProcessOneVTile` 第一步（:1312 调用 `LoadVBeta`，其内 :1345 把它重铸成 fp16 板）就被重新覆写，是 **per-tile** 暂存。

### 5.4 夹住的行区间与容量恒等

锚点：88d8b965/op_kernel/chunk_gated_delta_rule.h:170、185、765-767、815、820-833、2430-2433

容量恒等（这是"为什么是它"的第二半理由）。锚点：88d8b965/op_kernel/chunk_gated_delta_rule.h:170-185
（:171-184 之间夹着 `chunkScoresFp32`/`stateInFp32` 的分配与一个 `if/else` 分支，下面只取首尾两行、中间以省略号略过）：

```cpp
    ...
```

两者元素数**完全相同**，成员声明处的注释也相同（:2430 `// cs * avFp32 (v_beta, then v_new)`、

## 7. 借缓冲三条铁律（重述）

锚点：src/88d8b965/op_kernel/chunk_gated_delta_rule.h:765-767、813-833；docs/PR-1158-88d8b965/01-缓冲重叠Bug深度剖析.md:95-102

以下三条从 docs/PR-1158-88d8b965/01-缓冲重叠Bug深度剖析.md:95-102 吸收，用本文的机制语言重述，
并逐条标明它各自防的是**哪一种**覆盖。

**铁律一：同缓冲上的原地类型宽度变换一律禁止。**
防的是"**自己覆盖自己的未消费输入**"——dst 与 src 同基址、元素宽度不等时，
加宽方向写窗口比读窗口宽、写前沿必然越过读前沿；收窄方向反之，读窗口比写窗口宽、
后段源未消费就被写覆盖。两个方向都不可行，所以这条不需要逐例推演，直接当硬规则用。
合法的"原地"只在**同宽度**时存在（例如 fp16 视图搬 fp16 视图，本文件 `LoadChunkKey` 的 :765-767
就是安全先例：`keyLocal` 取 `chunkVFp32` 的 fp16 视图，DMA 后直接 `LoadPaddedRows` 写 `chunkKFp32`，全程无 Cast）。

**铁律二：借用之前，把该时刻的完整生命周期表重写一遍。**
防的是"**借了别人的活缓冲**"——错误类型不是算术而是"谁此刻持有这块内存"，
表现为写覆盖了仍在被读的活数据（WAR）。本例的正确答案不是"这块通常空着"，
而是能写出 §5 那张从 `ProcessChunkVTile` 调用序 → `PrepareAttnQueryCache:959` → `WriteAttnTileToGm:660`
的占用链，把借用区间夹进两次主人使用之间。
反面教训：`LoadChunkKey` 借 `chunkVFp32` 成功在先，!1135 在 `LoadChunkCoefficients` 里照抄同一手法，
却没照抄"那次借用是同宽度、无 Cast"这个前提。**不要抄上一处的答案。**

**铁律三：`ReinterpretCast` 之后，以字节为单位重画一遍内存图。**
防的是"**变量名暗示的布局与实际字节布局不一致**"——换视图后"一行"的宽度变了：
`chunkVFp32` 的一行是 `avStepAligned` 个 fp32 = `2·avStepAligned` 个 fp16，行号与元素号的对应关系整体漂移。
本 bug 的代码里 `DataCopy(betaLocal, ..., slabElements)` 与 `Cast(chunkVFp32, betaLocal, ..., slabElements)`
**两个调用各自参数都正确**，是它们的**地址别名组合**才错 ——
单看任一行都挑不出毛病，这正是这类 bug 难审的原因。
可执行的检查动作：把每条指令的读写区间写成 `[base + 2·i, base + 2·(i+n))` 与 `[base + 4·i, base + 4·(i+n))`
这样的闭区间，做一次相交判定，而不是靠读变量名。
