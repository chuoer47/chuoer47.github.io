# 11 · 成员变量与缓冲生命周期总表（2410-2461）

## 0. 结论先行

锚点：chunk_gated_delta_rule.h:2410-2461

1. **声明区相对 !1108 只增加了两行**：`:2421 GM_ADDR workspaceAddr_;` 与
   `:2437 LocalTensor<float> betaFp32;`。其余 50 行逐字节相同（`diff` 可证，见 §6）。
   **"只有两行变化"与"整个 kernel 的内存模型已经换了"同时成立**，
   因为改变的是这些句柄的**用法**（`ReinterpretCast` 借用点从 3 处涨到 21 处），不是声明。
2. **语义变化最大的不是新字段，而是 `:2442 alignK_` 与 `:2452 stateStrideK_`**：
   !1108 里两者是**两套对齐规则**（`Ceil(dk,16)*16` 与 `Ceil(dk,8)*8`，见 `00e39ab5:88-89`），
   !1135 里变成 `alignK_ = 桶宽`、`stateStrideK_ = alignK_`（`:91-92`），
   **即"K 的行宽"与"state 的行数"被强制统一到同一个编译期桶**。
   这一步是 `ComputeStateUpdateCube<kSpecializedDk, kSpecializedDk>`（`:2096`）
   能把 `kStateRows` 当模板常量用的前提。
3. **`:2423 stateOutQueue_` 的名字已经骗人**：它是 `TQue<QuePosition::VECOUT, 1>` 的单槽队列，
   在 !1135 里被**当成全 kernel 通用的 FP16 中转板**用了 8 个不同用途
   （state 输出、`StageHalf` hi、`StageHalfWithResidual` hi/lo、A 转置源、`final_state` Cast 目标……），
   `BUFFER_NUM = 1` 使每一次 `AllocTensor` 都必须配一次 `FreeTensor`——
   **漏掉一次 FreeTensor 就是死锁，多做一次就是踩数据**。
4. **`:2424 tmpBuff` 是唯一的 UB 大 buffer，12 个成员句柄全是它上面的视图**
   （`:161-202` 的 12 次 `GetWithOffset`），因此"两个成员同时存活"是假象：
   真正的约束是**偏移区间是否重叠 + 时间是否错开**。
   典型形状（B=1,H=16,T=128,dk=dv=128）下 tmpBuff 实占 **214784 B**、
   队列 **32768 B**，合计 247552 B（≈241.8 KiB，UB 256 KiB 的 94.5%），只剩 14592 B 空闲。
5. **chunkVFp32 是全场最忙的板**：声明注释只写了 `// cs * avFp32 (v_beta, then v_new)` 两个身份，
   实际快照里它至少承担 **11 种身份**（§5.2 逐条给锚点），
   包括被 `ReinterpretCast` 成 FP16 staging 4 次、被切成 5 块 scratch 2 次、当 L0C 落地板 2 次。
6. **风险清单 (c) 里唯一真实爆过的是 `:819` + `:827`**：
   `betaLocal` 与 Cast 目的端是**同一块 chunkVFp32**，FP16→FP32 是**原地增宽**，
   目标区间覆盖源区间且向后扩张，V 管按块前推时先写的 FP32 会毁掉尚未读的 FP16。
   !1158（`88d8b965:820`）的修法正是把 `betaLocal` 换成借 `chunkAttnOutFp32`；
   本仓库 048d0427（!1174）的 `:832/:840` 也是同一修法。
7. **为什么纯 Vector 时代这种借用安全、Cube 化后开始破**（§8 展开）：
   Vector 时代的每一步都自带 `PipeBarrier<PIPE_V>`，借用者与被借用者在**同一条管**上顺序执行；
   Cube 化引入了 M/MTE1/MTE2/MTE3 四条新流水与 L1/L0A/L0B/L0C 四级私有存储，
   **同一块 UB 现在可能被两个不同的管在两个不同的时刻读写，而代码里只写了同管栅栏**。

## 2. 队列与 UB 宿主（2422-2424）

锚点：chunk_gated_delta_rule.h:2422-2424

  典型形状 `max(128*128*2, 64*128*2) = 32768 B`。

  `:2351`（`final_state` 的 Cast 目标）、`:1045`（K 的 FP16 转置源）、
  以及 `:1562/:1563`、`:1585/:1586`、`:2354/:2355` 的 **EnQue+DeQue 当跨管栅栏用**。
  **命名与用途已经分离，03 章 Bug 清单里"队列槽位泄漏"一类风险都挂在这一行上。**

  `TPosition::VECCALC` 表明它占的是"向量计算"分区（与 `VECIN/VECOUT` 相对），
  但 !1135 把 MTE2/MTE3 的 DMA 目的/源也指到这里（`:823/:845/:1493/:2166` 等），
  **分区语义被当成了纯粹的地址空间用**。

- `:2429` `chunkVFp32 // cs * avFp32 (v_beta, then v_new)`：**全场最忙**，见 §5.2 与 §7。
- `:2430` `chunkScoresFp32 // cs * cs (attn matrix)`：与 `:2431` **同基址**（`:175-176`）。
- `:2431` `stateInFp32 // dk * avStepAligned (state [DK, vStep])`：

- `:2432` `chunkAttnOutFp32 // cs * avFp32 (output)`：还兼任 V 的 FP16 staging（`:1344`）、

- `:2433` `gCumsumFp32 // cs`：还是前缀和 ping-pong 的一端（`:791-807`）。
- `:2434` `deltaFp32 // temp: max(stateStrideK_, chunkSize_, vStepAligned_)`：

  身份最多：残差列（`:524`）、前缀和对端（`:792`）、衰减系数向量（`:2124-2128`）、

- `:2435` `dotProductFp32 // dot-product multiply/reduction scratch`：
  还被 `ReinterpretCast<uint32_t>` 当 gather 偏移表（`:525/:815`）。
- `:2436` `expGCumFp32 // precomputed exp(gCumsum) [cs]`：只被读（`:1185/:1950/:2065/:2122/:2298`），

- `:2437` **`betaFp32 // beta for the current chunk/head [cs]`（新增字段）**：

- `:2438` 空行。
- `:2439-:2441` `B_/T_/NK_`：批次、总序列长、QK 头数（`:78-80`）。
- `:2442` **`alignK_`——桶化后的语义改变者**。
  `:90-91`：`naturalAlignK = Ceil(dk,16)*16`；
  `alignK_ = (kSpecializedDk != 0 && dk <= kSpecializedDk) ? kSpecializedDk : naturalAlignK`。
  即**桶内：行宽 = 桶宽（64/80/96/128）**；桶 0 或 dk 超过桶宽：退回 16 对齐。
  它同时决定：`LoadPaddedRows` 的目的行宽（`:283/:296`）、
  高维 Mul 的 `rowStride`（`:884`）、`cs*alignK` 的缓冲容量（`:161/:164`）、

  这就是为什么它的注释只写 `uint32_t alignK_;` 而必须靠本篇把它的作用域列出来。
- `:2443` `realK_ = tilingData->dk`（`:81`）：**真实**头维，一切 `%16`、`<= 桶宽` 判断的左值
  （`:259/:2361/:2372`）。
- `:2444-:2446` `NV_/realV_/vStep_`：value 头数、真实 Dv、每片 V 步长（`:82-83/:88`）。
- `:2447-:2448` `chunkSize_/numChunks_`：块长（当前恒 64）与块数。
  **`chunkSize_` 是 `kMatmulM/kMatmulK = 64` 这些"魔数"的真实来源**
  （`ComputeOutputCube:1926-1927` 把 64 写成了 `constexpr`，与 `chunkSize_` 是重复表达，
  靠 `IsCubeFastPath:259` 的 `chunkLen == 64` 保证一致）。
- `:2449` `hasGamma_`：可选 g 的存在位（`:87`）。
- `:2450` `restUbSize_ = tilingData->ubRestBytes`（`:89`）：
  host 侧 `SolveVStep` 算出的 `ubSize - outQueueMax`（`02b 章 §SolveVStep`），
  **tmpBuff 的容量就是它，多出来的 14592 B（典型形状）是 `GetWithOffset` 借用的安全垫**。
- `:2451` `vStepAligned_`：`Ceil(vStep_, 8)*8`，在 `InitLocalBuffers:135-136` 才赋值，
  构造里置 0（`:100`）。**全 kernel 用 `avFp32`/`vStepAligned_` 两个名字指它**

- `:2452` **`stateStrideK_`——语义被简化成 `alignK_` 的别名**（`:92` `stateStrideK_ = alignK_;`）。
  !1108 里它是独立的 `Ceil(dk,8)*8`（`00e39ab5:89`）。
  现在它的用途是：`stateInFp32` 的行数（`:176/:181`）、

  **注意它不影响 workspace 布局**（那是 `stateWorkspaceStrideV_`），

- `:2453` `stateWorkspaceStrideV_ = Ceil(dv,8)*8`（`:93`）：workspace 的行宽，

- `:2454-:2456` `load_/usedblk_/avgload_`：负载均衡游标（`IsCurrentBlock:342-350`、

- `:2457` `scale_`：`1/sqrt(dk)` 类 attr（`:84`），在 `:1950` 与 `:959` 被吸收进 Q 的行缩放。
- `:2458` `blockIdx_`：`GetBlockIdx()`（`:107`），**Cube staging 槽位分配的唯一依据**

三点核对说明：

- **scores 与 state 同基址**：`:173-177` 的 `if (vStep_ >= realV_ || ShouldSplitVTiles())` 在
  `vStep_ == realV_ == 128` 时成立，两块都用**未自增的 `off`**（`:175` 与 `:176`），
  只推进 `overlapSize`；`overlapSize = max(cs*cs, stateStrideK_*avStepAligned) = max(4096,16384) = 16384`。
  这是全表**唯一一对静态重叠**，理由是"scores 的最后一次读在 `ComputeVNew`，
  而 state 的第一次写在 `LoadStateTile`"（注释 `:150-152`）。
- **80 桶的 125312 与实测日志一致**：`docs/PR-1135-d0906c3e/02-实验复现.md` 记录
  `d0906c3e: dk=80, vStep=80, tbuf=125312`。本表逐列相加
  `20480+20480+16384+20480+25600+20480+256+320+320+256+256 = 125312` ✓，
  说明本表不是估算而是与 host 侧 `ComputeTmpBuffBytes`（`02b 章`）同构的重算。
- **余量**：`restUbSize_ = ubSize - outQueueBytes`，128 桶下 tmpBuff 被要求 214784 B，
  而 `InitBuffer(tmpBuff, restUbSize_)`（`:158`）给的是全部余量；
  表内偏移累加到 214784，**剩下的字节没有被任何具名句柄占用**，
  只被 `:2253` 的 `tmpBuff.GetWithOffset<float>(kStateElements, 0)` 这类"从 0 号偏移借三块板"的写法引用。

## 8. 结论：为什么这套借用在纯 Vector 时代安全、Cube 化之后开始破

**纯 Vector 时代（!1108）的隐含契约有两条，且都自动成立**：
(1) 所有算术都在 V 管上顺序执行，任意两次指令之间只要有一条
`PipeBarrier<PIPE_V>`（本文件的 fallback 几乎每条 `Mul/Axpy/Exp` 后都跟一条，
如 `:895/:906/:908/:933/:1200/:1204/:2302/:2313`），就**不存在乱序可见性**；
(2) UB 上任何一个时刻只有一条流水在写，所以"借用哪块板"只取决于**程序顺序上的最后一次读**——
这是一个纯文本可判定的条件，人眼 review 就够用。
!1108 里 `chunkVFp32` 的借用点只有 3 处（`:522/:563/:599`），全部在同一个函数族内部，
所以它的声明注释"v_beta, then v_new"与实际用法是一致的。

**!1135 把这两个前提同时打断了**：

- **流水变多**：V 之外多了 M、MTE1、MTE2、MTE3。
  同一块 UB 现在既可能是 V 的算术目的地，也可能是 MTE2 的 DMA 目的、MTE3 的 DMA 源、
  甚至 M 管 L0C 的读回落地点（`:2258`）。
  **`PipeBarrier<PIPE_V>` 对 MTE3 完全无效**，必须换成 `SetFlag/WaitFlag<V_MTE3>`（`:2163-2165`）
  或 `PipeBarrier<PIPE_ALL>`（`:2259`）——这正是 10b §9 里 L0C 读回只能用全管栅栏的原因，
  也是 !1174 的 `L0C read/write conflict` 事故（`docs/PR-1174-048d0427/01` §1）的根因形态。
- **借用点从 3 处涨到 21 处，且横跨函数边界**：`chunkKFp32` 在 `ComputeOutputCube` 里是 Q 板、
  在 `ComputeStateUpdateCube` 里是 K 板再到残差板再到 `cNz`。
  **"最后一次读"从"往上看 30 行"变成"要跨 500 行、4 个函数、逆着 `ProcessOneVTile` 的调用序去推"**，
  人眼 review 不再可靠——表 (c) 的 #7 就是这次失效的实证，
  它在 !1135 初版（`a9c66ddb:768/:776`）就已存在，直到 !1158 才被独立的精度事故暴露。
- **增宽写成为可能**：Vector 时代的借用**类型不变**（FP32 板借给 FP32 scratch），
  覆写窗口 = 读取窗口。Cube 时代要 `ReinterpretCast` 成 FP16 当 staging、
  再 `Cast` 回 FP32（`:819 → :827`），**同一次借用把目标撑到源的 2 倍宽**，
  于是"源区间是目的区间的真子集"这种在 Vector 时代不可能出现的拓扑出现了。
  这是 !1158 的机制级原因，而不是"某行写错了"。
- **不变式没有被写下来**：容量守卫分散在 `:763/:946/:1478/:2372`，
  每处只检查**自己那一块**的地址范围，没有任何一处检查"这块板现在属于谁"。
  全文件唯一写成注释的借用声明是 `:1466-1467` 与 `:2251-2252` 两处，
  **其余 19 处借用点没有一行注释**。

**因此本篇的三条可执行结论**：
① 任何新增借用必须像 `:1466-1467` 那样**写明出借方已死 + 最后一次读的行号**；
② 跨管复用（V 写 → MTE3 读 → V 再写）必须有 `SetFlag/WaitFlag` 或 `PIPE_ALL`，
   同管复用只能靠 `PIPE_V`——判据是"借用者与被借用者在不在同一条管上"；
③ **禁止在同一块 UB 上做类型增宽的原地写**（表 #7 的唯一根治法），
   需要临时增宽就换一块板，代价只是多一次 `Cast`。
   本篇从声明区把它们重新推导了一遍。
